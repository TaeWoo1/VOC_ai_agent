# `review-issue/v1` — 반복 이슈 변화 탐지 임계값 계약

> ## ⚠ 상태: 초안 (DRAFT) — 제품 오너 확정 전
>
> 아래 숫자는 **제안**이며 확정된 결정이 아니다. 그리고 **어떤 실제 결과로도 검증되지 않았다** —
> 검증할 수 없는 것이 아니라, 결과를 보기 전에 정하는 것이 이 문서의 목적이기 때문이다(아래 참조).
> 따라서 다음을 주장해서는 안 된다:
>
> - 이 임계값이 옳다는 주장
> - 이 임계값으로 내린 판정의 정확도가 측정되었다는 주장
> - 판정을 만들어내는 추출기의 성능이 검증되었다는 주장 —
>   `contracts/review-eval/naver/v1/labels.json`은 여전히 **비어 있다**
>
> 자동 테스트와 `tools/review-issue-validation/`의 일회용 백엔드 검증이 확인하는 것은
> **동작(behaviour)**이다: 판정이 계약이 정의한 윈도에서 발화하는가, 억제 규칙이 지켜지는가,
> 재실행이 멱등한가, 확인 필요 큐가 변하지 않는가. **판정이 옳은가는 확인하지 않는다.**

이 문서는 `review-eval/naver/v1/RUBRIC.md`와 같은 이유로 존재한다:

> 결과를 본 뒤에 합의된 임계값은 임계값이 아니다.

`RUBRIC.md`가 detector가 존재하기 전에 bar를 못박은 것처럼, 이 문서는 변화 탐지 코드가 첫 판정을
내리기 전에 "무엇을 급증이라 부를 것인가"를 못박는다. 숫자를 나중에 조정하는 것은 허용된다 —
**결과를 보고 조정하면서 그것을 원래 기준이었던 것처럼 말하는 것**이 금지된다. 조정은 이 문서의
버전을 올리고 이유를 남긴다.

---

## 0. 이 계약이 다루지 않는 것

- **무엇이 하나의 이슈인가**(signature 추출·매칭 품질)는 이 문서의 범위가 아니다. 그것은
  `review-eval/naver/v1`의 관할이고, 그 seed는 아직 비어 있다.
- 따라서 이 문서의 모든 판정은 **"이슈 배정이 옳다고 가정할 때, 그 이슈의 시간적·구조적 변화를
  어떻게 부를 것인가"**에 대한 것이다. 배정이 틀리면 판정도 틀린다. 이 의존성은 감춰지지 않는다.
- **원인 추정은 어떤 판정에도 포함되지 않는다.** 판정은 "이 이슈의 근거가 이렇게 변했다"까지이며
  "무엇 때문에"는 말하지 않는다.

## 1. 시간 단위 — 왜 하루인가

리뷰의 `received_at`은 파일 임포트 경로에서 **날짜 단위로 저장된다.**
`DateParse.localDate`가 시각 성분을 명시적으로 버리고(`raw.strip().split("[ T]")[0]`),
`instantAtStartOfDay`가 UTC 자정으로 고정한다.

따라서:

- **모든 윈도는 일(day) 단위**다. 시간 단위 윈도는 데이터에 존재하지 않는 정밀도를 가정하는 것이다.
- 버킷팅은 `received_at`의 **UTC 날짜**로 한다. 파일 임포트 행에 대해 이 값은 채널이 표시한 달력
  날짜와 **정확히 일치**한다(자정 UTC로 저장했으므로 되읽으면 같은 날짜).
- ⚠ 향후 실제 타임스탬프를 주는 API 소스가 추가되면 이 등식이 깨진다. 그때는 타임존 결정을
  **명시적으로** 내려야 하고, 그 전까지 코드는 소스별 시각 정밀도를 가정하지 않는다.
- 기준 시각(`now`)은 **항상 호출자 파라미터**다. 판정 로직 안에서 벽시계를 읽지 않는다
  (collector의 recency 레이어와 같은 규칙 — 테스트 가능성이 이 규칙의 목적이다).

기본 관찰 윈도는 **7일**이고 주간 리포트 주기와 정렬한다.

## 2. 네 가지 판정

운영자에게는 이 네 개만 보인다. 서로 겹칠 수 있다(예: `증가 중 · 특정 옵션 집중`).

### 2.1 신규 등장 (NEW)

| 파라미터 | 값 |
|---|---|
| `NEW_WINDOW_DAYS` | **14** |
| `NEW_MIN_EVIDENCE` | **3** |
| 사전 조건 | 윈도 시작 이전에 이 이슈의 근거가 **0건** |

**왜 14일인가.** 7일이면 새 이슈가 주 경계를 걸쳐 3건을 모으는 동안 계속 카운트가 리셋되어
**영구히 발화하지 않는다**. 신규 판정만 관찰 윈도보다 길다.

**왜 3건인가.** 1건은 이슈가 아니다 — 리뷰 한 건으로 새 운영 이슈를 선언하지 않는 것은 제품
원칙이다. 2건은 우연한 동시 발생이 흔하다. 3건은 여정 문서의 "10일 4건"보다 약간 민감하되,
14일 윈도와 결합하면 발생률이 비슷하다.

**"이전에 0건"이 엄격한 이유.** 이 조건이 없으면 오래된 이슈가 조용한 구간을 지난 뒤 신규로
재선언된다. 운영자에게 "이전에 없던 문제"라고 말하는 것은 사실 주장이므로 사실이어야 한다.

### 2.2 급증 (SURGING)

| 파라미터 | 값 |
|---|---|
| `SURGE_WINDOW_DAYS` | **7** |
| `SURGE_BASELINE_WEEKS` | **8** (관찰 윈도 직전 8주) |
| `SURGE_MIN_CURRENT` | **4** |
| `SURGE_MIN_BASELINE_TOTAL` | **4** (8주 합계) |
| `SURGE_RATIO` | **2.0** |
| `SURGE_HIGH_CURRENT` | **8** |
| `SURGE_HIGH_RATIO` | **3.5** |

baseline = (직전 8주 근거 합계) / 8 = 주당 평균.
발화 조건: `current >= 4` **AND** `baseline_total >= 4` **AND** `current >= baseline * 2.0`.

**기존 규칙과 다른 점, 그리고 왜.** `AttentionSignalRules.spike`는 **직전 동일 길이 윈도 1개**를
baseline으로 쓴다(채널 전체 리뷰량 대비). 이슈 단위 카운트는 훨씬 작아서 직전 1주는 잡음이 크고,
0인 주가 흔하다. 그래서 **8주 평균**으로 바꾼다. 구조(최소 현재값 + 최소 baseline + 비율)는
기존 규칙을 그대로 따르며, 특히 `baseline_total >= 4` 요구는 기존 규칙의 `previous >= 1`과 같은
목적이다 — **`0 → N`은 절대 급증으로 발화하지 않는다.** 갓 연결한 계정이 모든 이슈에서 급증
알림을 쏟아내는 것을 막는다.

⚠ **평균의 알려진 취약점.** 8주 중 한 주의 과거 스파이크가 baseline을 끌어올려 진짜 급증을
가린다(위음성). 중앙값이 더 강건하지만, 저빈도 이슈에서 주간 중앙값은 대개 0이 되어 비율이
정의되지 않는다. **평균 + 최소 합계**를 택한 것은 이 트레이드오프의 결과이며, 위음성 방향으로
기울인 것은 의도적이다(precision 우선).

### 2.3 계속 발생 (PERSISTENT)

| 파라미터 | 값 |
|---|---|
| `PERSIST_LOOKBACK_WEEKS` | **6** |
| `PERSIST_MIN_ACTIVE_WEEKS` | **4** (6주 중) |
| 배타 조건 | SURGING이면 PERSISTENT로 표시하지 않는다 |

"근거가 1건 이상 있는 주"가 최근 6주 중 4주 이상.

**"6주 연속"을 쓰지 않는 이유.** 여정 문서는 연속을 말하지만, 엄격한 연속성은 조용한 한 주
(연휴, 판매 저조, 임포트 누락)가 6주치 신호를 지운다. 운영자의 질문은 "매주 빠짐없이
발생했는가"가 아니라 **"이게 아직도 일어나고 있는가"**다. 6주 중 4주는 그 질문에 답한다.

⚠ 임포트 공백이 조용한 주와 구별되지 않는다. 리뷰가 없는 주와 **가져오지 않은** 주는 카운트가
똑같이 0이다. Phase A는 이를 해결하지 않고, 판정에 커버리지 공백이 섞일 수 있음을 기록만 한다.

### 2.4 특정 상품 집중 (CONCENTRATED)

| 파라미터 | 값 |
|---|---|
| `CONCENTRATION_WINDOW_DAYS` | **28** |
| `CONCENTRATION_MIN_TOTAL` | **5** |
| `CONCENTRATION_SHARE` | **0.60** |

윈도 내 이슈 근거 총 `>= 5` **AND** 최다 상품의 점유율 `>= 0.60`.

**최소 5건이 없으면 이 판정은 자기 목적에 대해 공허하다.** 근거 1건이면 점유율은 항상 100%이고,
"특정 상품에 집중됐다"가 무조건 참이 된다. 이것은 `RUBRIC.md` §4의 세 번째 adequacy 조건이 닫은
구멍과 **정확히 같은 종류**다 — 표본이 없는 곳에서 `0/0`이 0.00으로 읽혀 게이트가 통과되는 것.
같은 실수를 다른 이름으로 반복하지 않기 위해 하한을 둔다.

**왜 28일인가(급증은 7일).** 집중은 시간적 성질이 아니라 **구조적** 성질("어느 상품인가")이고,
구조 추정은 더 많은 표본을 요구한다. 7일 윈도에서 상품 점유율을 말하면 대부분 표본 부족이다.

**옵션 단위는 Phase A 범위 밖.** `reviews`에 옵션 컬럼이 없고 `ReviewRowMapper`가 옵션을 매핑하지
않는다. 판정은 **상품 단위**이며, 화면 문구도 상품 단위여야 한다. NAVER export에 옵션 컬럼이
실제 존재하는지는 실파일 증거로만 확인할 수 있는 미해결 항목이다.

## 3. 개선 (IMPROVED) — 리포트 전용, 알림 아님

| 파라미터 | 값 |
|---|---|
| `IMPROVE_WINDOW_WEEKS` | **4** (현재 4주) |
| `IMPROVE_BASELINE_WEEKS` | **4** (그 직전 4주) |
| `IMPROVE_MIN_BASELINE_WEEKLY` | **2.0** (주당) |
| `IMPROVE_MAX_RATIO` | **0.40** |

여정 문서의 예(주 5.2건 → 주 1.3건 = 0.25×)는 이 기준에서 발화한다.

**개선을 알림으로 보내지 않는 이유.** 좋은 소식은 방해할 이유가 없다. 주간 리포트에 속한다.
그리고 개선은 SellerOps가 경고만 만드는 서비스가 아님을 보이는 유일한 항목이므로 리포트에서
**빠지지 않아야** 한다.

## 4. 생명주기 — 자동 전이는 두 개뿐

```
관찰 중 → 확인 필요 → 조치 중 → 개선 확인 중 → 해결됨
```

| 전이 | 주체 |
|---|---|
| 관찰 중 → 확인 필요 | **자동** — NEW / SURGING / PERSISTENT / CONCENTRATED 중 하나라도 발화 |
| 확인 필요 → 조치 중 | **운영자만** |
| 조치 중 → 개선 확인 중 | **운영자만** (조치를 마쳤다고 기록할 때) |
| 개선 확인 중 → 해결됨 | **자동** — `RESOLVE_QUIET_WEEKS` = **4**주 연속 신규 근거 0건 |
| 임의 → 관찰 중 | **자동** — 해결됨 이후 근거가 다시 붙으면 재개(신규로 재선언하지 않는다) |

**해결됨은 소멸 주장이 아니다.** 문구는 다음 형태만 허용한다:

> 최근 4주간 관련 리뷰가 확인되지 않아 현재 해결된 상태로 표시했습니다.

`완전히 해결되었습니다` / `문제가 사라졌습니다` / `원인이 제거되었습니다`는 금지한다.
4주 침묵은 부재의 증거가 아니라 **부재의 관찰**이다.

**해결됨 자동 전이가 개선 확인 중에서만 일어나는 이유.** 운영자가 아무 조치도 하지 않은 이슈가
조용해졌다면 그것은 해결이 아니라 판매 저조·계절성·임포트 공백일 수 있다. 조치 기록이 있는
이슈만 자동으로 해결됨에 도달한다.

## 5. 알림 라우팅 — Phase A에는 즉시 알림이 없다

| 채널 | 내용 |
|---|---|
| **즉시** | **(Phase A: 없음)** |
| **일일 요약** | 신규 근거가 붙은 이슈, 새로 발화한 NEW / SURGING / CONCENTRATED, 답변 필요 리뷰 수 |
| **주간 리포트** | 네 판정 전체 + IMPROVED + 미처리 답변 + 다음 주 우선 확인 |
| **알림 없음** | 평소 범위 내 기존 이슈, 근거 1–2건의 미발화 후보, 긍정 리뷰 증가, 운영자가 무시·종료한 이슈 |

**즉시 알림을 비운 것은 제품 오너 확인이 필요한 판단이다.** 이유:

1. 여정 문서가 즉시 알림의 첫 근거로 든 **"안전과 관련된 심각한 표현"**은 텍스트 의미 판정이며,
   D1(LLM 게이트) 없이는 키워드로만 가능하다. 그리고 이것이 정확히 `RUBRIC.md`가 인용한 phase2e
   실패 지점이다 — 0/30 recall, surface-form rigidity. **가장 높은 위험의 판정을 가장 약한 방법으로
   하는 것**이고, 실패 방향이 최악이다(안전 이슈 누락).
2. 나머지 즉시 근거(급증)는 **7일 윈도 판정**이다. 7일에 걸쳐 축적된 신호는 본질적으로 사람을
   중단시킬 만한 것이 아니다. 즉시로 보내면 "즉시"의 의미가 닳는다.

따라서 Phase A는 즉시 알림을 **의도적으로 비워 두고**, 안전 판정은 D1 이후로 미룬다.
즉시 알림이 필요하다고 판단되면 그 근거가 무엇인지 먼저 정해야 한다.

## 6. 정직성 규칙 (판정 문구)

- 커버리지 공백과 침묵을 구별할 수 없다는 사실을 숨기지 않는다.
- 카운트는 판매자 대면 화면에서 정확한 수치로 노출할 수 있다(scope v1.4 ③ 예외).
  **단 같은 수치가 로그·커넥터 출력·리포트 파일로 나가면 위반**이다(roadmap §9: exact row count 금지).
- 판정은 **이슈 후보 · 운영 신호**로 표현한다. 진단이 아니다 — `ProductIssues.tsx`가 이미 지키는 규칙.
- 어떤 판정도 원인을 지목하지 않는다. `이 옵션에서 문제가 집중되고 있습니다. …를 먼저 확인해
  보세요`는 허용, `…가 원인입니다`는 금지.

## 7. 미해결 (제품 오너 결정)

1. **§5 즉시 알림을 비워 두는 것** — 승인 필요.
2. **§2 숫자 전체** — 위 값은 초안이다.
3. **NAVER export의 옵션 컬럼 존재 여부** — 실파일 증거 필요. 있으면 §2.4가 옵션 단위로 승격.
4. **임포트 공백 vs 조용한 주 구별** — Phase A 범위 밖. 해결하려면 커버리지 데이터
   (`review_import_segment`)를 판정에 결합해야 한다.
