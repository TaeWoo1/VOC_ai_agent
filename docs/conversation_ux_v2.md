## 0. 이 패키지가 답하는 질문

PO QA는 여섯 가지를 말했다. 예시 문장별 patch로 닫으면 다음 문장에서 같은 자리가 다시 깨지므로,
먼저 **공통 원인**을 찾았다. 여섯 증상은 네 개의 원인에서 나온다.

| 관측된 증상 | 공통 원인 |
|---|---|
| 「현금영수증 관련 문의 중 가장 최근 문의」가 topic을 잃고 전역 최신 문의를 반환 | **질문의 주어를 담을 자리가 닫힌 5-값 enum 하나뿐**이었다 (§1) |
| 「미응답 문의 중 가장 시급한 건?」이 20건 전체를 나열 | **작업 어휘에 순위 mode가 없었다** — 최상급 질문이 취할 수 있는 유일한 모양이 목록이었다 (§2) |
| 문의 row를 선택해도 본문이 바로 보이지 않음 | **본문 읽기가 work item에 묶여 있었다** — 답변된 문의는 work item이 없다 (§3) |
| 답변이 시스템 상태·카드·근거 숫자를 반복 / Knowledge Gap이 여러 UI로 반복 / admin SaaS 느낌 | **「한 사실은 한 번만 말한다」는 규칙이 없었다** — lane마다 더하기만 했다 (§4) |

## 1. 주어(SUBJECT) — 판매자가 쓴 낱말이 읽기에 닿는다

**결함.** 질문의 주어를 표현하는 자리는 `filters.topic` 하나였고, 그것은 닫힌 다섯 가족
(배송 · 교환반품 · 규격 · 사용법 · 기타)이다. 판매자가 **현금영수증 · 세금계산서 · 파손 · 색상 · A/S**를
말하면 플래너가 넣을 칸이 없어 그 낱말은 **조용히 사라지고**, 읽기는 더 넓은 질문에 답한 뒤 그것을
원래 질문의 답인 것처럼 확신 있게 말했다. enum에 값을 하나 더 붙이는 것은 **다음 낱말에서 같은 결함**이다.

**설계.** 축을 하나 늘리되 그것은 토큰이 아니라 **판매자 자신의 낱말**이다.

- `conversation/subjectTerm.ts` — 문장이 그 낱말을 **주어로 표시했을 때만**(「X 관련」·「X에 대한」·
  「X 문의」) 가져오는 닫힌 추출기. 모델 호출 0, 추측 0: 결과는 판매자가 친 문자열의 부분 문자열이다.
  이미 자기 축을 가진 낱말(채널·기간·정렬·상태·topic 가족)과 행을 서술하는 동사형(들어온·밀린·처리할)은
  **거부**한다 — 실패 방향은 항상 「좁히지 않음」이고 결코 「잘못 좁힘」이 아니다.
- **플래너는 이 낱말을 모른다.** plan schema는 그대로 닫힌 토큰만 갖고, 프롬프트는 오히려 반대로
  가르친다: 「다섯 값에 맞지 않는 주제면 topic 은 null 로 두세요 — 그 낱말은 런타임이 판매자가 쓴 그대로
  좁힙니다」. payload floor 무변경.
- 읽기: `GET /api/inquiries/rows?q=` — 제목 **또는** 본문에 대한 **하나의 bound LIKE**. 문장이 SQL이 되는
  경로는 없고 (`MAX_TERM` 40자, 그보다 길면 자르지 않고 거절), 반환 행은 그대로 sanitized다.
  작업 큐(`list_inquiry_workload`)도 같은 낱말을 in-process로 적용한다.
- **좁힌 낱말은 되말한다** — 「현금영수증 관련 문의는 3건입니다」. 그래서 그 아래의 0은 **그 주제에
  대한 0**이고, 조용한 확대가 될 수 없다.
- 화면 위 집합에도 같은 축이 있다: 결정론 FILTER lane이 **leftover 한 낱말**을 주어로 받는다
  (「그중 현금영수증만」). 두 개 이상 남으면 이 표들이 읽을 수 없는 문장이므로 플래너의 것이다.

**부수 효과 하나 — NEW_SUBJECT.** 「파손 문의」 집합 위에서 「교환 문의는?」이라고 물으면 플래너는 그것을
직전 집합의 refine으로 계획했고, 답은 「방금 본 문의 중 교환 관련은 없습니다」였다. 산술적으로 참이고
운영적으로 거짓이다 — 두 주제는 구성상 서로소이고, 판매자는 **조직에 새 질문**을 한 것이다.
`scopeOverride`에 네 번째 이유 **`NEW_SUBJECT`**를 더했다: 집합이 **이미 주어를 갖고 있고** 문장이
**다른** 주어를 이름 지으면 scope는 ORG가 되고 물려받은 축도 함께 떨어진다(닫힌 값 비교, 문장 읽기 0).
주어가 **없던** 집합을 주어로 좁히는 것은 여전히 진짜 refine이다.

## 2. PRIORITIZE — 순서를 묻는 질문에는 순서와 그 이유로 답한다

**결함.** ConversationTask에는 LIST · FILTER · INSPECT · ANALYZE · PREPARE · REVISE · EXECUTE가 있었고
**순위가 없었다.** 그래서 「가장 시급한 건?」이 표현될 수 있는 유일한 모양이 목록이었고, 답은 20행이었다.

**설계.** mode를 더하되 **기준을 말하는** mode로.

- 닫힌 plan 토큰 `inquiryIntent = "PRIORITY"` (프롬프트 v9). 최상급 표현(「가장 최근 문의」·「제일 오래된
  건」)은 `limit=1`이라는 규칙도 함께 적었다 — 개수를 말하지 않았어도 하나를 물은 것이다.
- `conversation/urgency.ts` — **기준은 하나이고 그것은 문장으로 나온다**: 「고객이 기다린 시간을 기준으로
  정했습니다.」 + 「채널이 정한 답변 기한 정보는 아직 없어 대기 시간만 봅니다.」 이 제품이 실제로 가진
  urgency 신호는 대기 시간뿐이고(레거시 그래프의 감사 결과를 재확인), 데이터가 받쳐 주지 않는 판단을
  암시하지 않는 것이 이 mode의 계약이다. 모델 호출 0 · 추가 읽기 0.
- 행마다 **왜 거기 있는지**가 붙는다 — `waitingDays` (「34일째 대기」).
- 화면 위 집합에도 같은 mode: 「그중 급한 것부터」·「뭐부터 봐야 해?」는 결정론 lane이 즉시(LLM 0, 읽기 0)
  정렬한다. 다만 문장이 **자기 scope를 이름 지으면**(「미응답 문의 중…」·「오늘 …」) 플래너의 것이다 —
  화면 위 집합으로 답하면 질문이 조용히 좁아진다.

## 3. 선택한 행은 고객이 쓴 문장을 보여 준다

**결함 두 개.**
1. 본문을 읽는 유일한 경로가 `GET /api/inquiries/{workItemId}`였는데 **답변된 문의에는 work item이
   없다** — 그런 행을 고르면 제목만 남았다.
2. 서수에 **보는 동사**가 붙으면(「두 번째 거 자세히 보여줘」) 결정론 선택 lane이 거절했고, 플래너가
   조직 큐를 다시 읽어 **목록 전체를 「선택한 문의」 카드 아래 다시 인쇄**했다.

**설계.**
- 행 자체가 고객의 첫 문장을 들고 온다 — `InquiryRowItem.snippet` / `InquiryQueueItem.snippet`,
  문의 피드가 이미 쓰는 **같은 마스킹**(`InboxService.snippet`, 전화·이메일 마스킹 후 절단). 목록을
  **읽을 수 있게** 만드는 한 줄이고, work item 유무와 무관하다. 대화 저장 시에는 **벗겨진다**
  (`persistableArtifact`) — 스레드는 고객 문장의 두 번째 사본을 쌓지 않는다.
- 그래서 화면 위에서 한 턴 전에 읽히던 행이 refine 뒤에 제목만 남는 문제가 생긴다 ⇒
  `frontend/src/lib/conversation/snippetCache.ts` — **이 페이지가 이미 그린 문장**의 메모리. 저장소가
  아니고(디스크·localStorage·전송 0) 새로고침이면 비며, 세션/org 전환에서 지워진다.
- 서수 + 보는 동사는 여전히 선택이다(닫힌 viewing tail). 서수 + **행동** 동사(답변 준비·보내·말투)는
  그대로 플래너의 것이다.
- 플래너가 행 하나를 지목해 해결했을 때도 답은 **그 행**이다: 곁에서 읽은 목록은 지우고
  INSPECT lane과 **같은 카드**를 그린다.

## 4. 한 사실은 한 번만 — 답 → 이유/제약 → 다음 행동

새 컴포넌트도 새 프레임워크도 아니다. **같은 사실을 두 번 말하는 자리를 지운다**는 규칙 하나다.

| 지운 중복 | 어디서 |
|---|---|
| 초안 없는 DRAFT 카드 (제목·본문이 그 턴의 문장 그대로) | `DraftArtifact` — `version == null`이면 **아무것도 그리지 않는다** |
| 빈 목록 카드 「보여드릴 문의가 없습니다」 | `InquiryListArtifact` — 행이 0이면 그리지 않는다 (문장이 이미 말했다) |
| Knowledge Gap 질문이 산문과 카드에 두 번 | `KnowledgeCaptureArtifact` — `ASKED`는 **아무것도 그리지 않는다** |
| 「저장 전에는 아무것도 바뀌지 않습니다」가 산문과 카드에 두 번 | 카드에서 제거 |
| 「답변하려면 답변 기준이 필요합니다」(제목)와 「…답변 기준이 없습니다」(설명) | `KNOWLEDGE_ENTRY`는 설명 줄 없음 |
| 초안 카드의 「말투 다듬기」·「보내기 준비」를 칩이 반복 | 칩 제거 — 카드가 그 두 행동의 주인 |
| 화면에 이미 있는 링크를 반복하는 「전체 N건 처리하기」 | 목록 카드가 같은 곳을 가리키거나 행이 1건이면 칩 없음 |
| 순위 문장을 headline과 finding이 각각 조립 | 하나의 `urgencySentence()`를 양쪽이 읽는다 |
| supporting finding 4개 | 2개 |
| 「근거 N」의 숫자(그 N은 읽은 행 수이지 근거의 강도가 아니다) | 숫자 제거 |
| 재개할 수 없는 단계에 붙던 「계속 확인하기」 | `resumable`인 단계에만 |
| 방금 거절된 요청을 되풀이하는 칩 | 사람이 할 일이 있는 턴은 **그 단계만** 제안한다 |
| lane이 정한 다음 행동 위에 일반 집합 칩이 덧붙던 것 | 자기 다음 행동을 이름 지은 lane이 그것을 소유한다 |

칩은 자기가 설명하는 집합을 따른다 — 1건에는 「첫 번째」가 없고, 이미 급한 순으로 정렬된 집합에
「가장 최근 1개」를 다시 권하지 않는다.

**정정 하나.** 저장한 규칙으로 초안을 다시 만들 수 없었을 때 카드는 항상 「이 문의에 바로 적용할 근거로는
아직 부족합니다」라고 말했다. 초안 기능 자체가 이 배포에서 꺼져 있어 **시도조차 되지 않은** 경우에는
그것이 판매자 자신의 규칙에 대한 **틀린 진술**이다 ⇒ 그 경우 카드는 resume 줄을 달지 않고, 산문이 진짜
이유를 한 번 말한다.

## 7. 고치지 않고 보고하는 것

1. **`snippet`은 대화에 저장되지 않는다.** 새로고침한 스레드의 목록 행은 다시 제목만 남고, 행을 펼치면
   그때 상세를 읽는다. 고객 문장의 두 번째 사본을 스레드에 쌓지 않기 위한 의도된 성질이다.
2. **플래너 변동성.** 같은 문장이 실행마다 다른 need/intent로 계획될 수 있다(§5 A5가 실제로 그랬다).
   프롬프트 규칙으로 좁혔을 뿐 결정론이 아니며, 결정론 lane들이 닿지 않는 문장은 이 변동성을 그대로 진다.
3. **순위 기준은 대기 시간 하나다.** 채널별 답변 기한, 문의 심각도, 반복 문제와의 연결은 이 제품이
   아직 갖고 있지 않다. 답변이 그렇게 말한다.
4. **PRIORITIZE는 문의만.** 리뷰·주문에는 순위 mode가 없다.
5. **`q`는 부분 문자열이다.** 형태소 분석도 동의어도 아니므로 「영수증」은 「현금영수증」을 찾지만
   「현금 영수증」(띄어쓰기)은 찾지 못한다. 판매자가 쓴 낱말 그대로만 좁힌다.
6. **QA org와 배포 설정은 원복했다.** org 행 삭제(문의·work item·계정·조직), `backend/.env.local`은
   백업과 byte-identical, 스택 재기동 확인.
7. **초안 lane은 배포 설정에 달려 있다.** 기본 배포에서 꺼져 있으면 §5 D3·D4는 「AI 답변 초안 기능이
   켜져 있지 않습니다」로 끝난다 — 이 패키지가 바꾼 것은 그때의 **문장 수**뿐이다.
