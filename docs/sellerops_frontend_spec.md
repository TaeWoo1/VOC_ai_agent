## 1. 목적과 범위

- 본 문서는 **Seller Track 프론트엔드**(`frontend/` — React 18 + TypeScript + Vite + Tailwind SPA)의
  리디자인 스펙이다. Manufacturer VOC Track은 장기 방향으로서 **혼입 금지**
  (`product-scope-v1.md` §3).
- 목표 인상: **여러 커머스 플랫폼을 하나로 합친 통합 셀러센터.** 기술 커넥터 콘솔이 아니라,
  셀러가 매일 여는 운영 화면.
- v1 기능 경계는 범위 문서를 따른다: **읽기·식별·우선순위까지**(채널 쓰기 없음), 데이터 다섯 종
  (주문·문의·리뷰·상품·운영 리포트).
- 본 문서가 다루는 것: 사용자·여정·IA·화면·상태 규칙·언어·접근성·슬라이스. 다루지 않는 것:
  수집 전략(커넥터 로드맵), 백엔드 설계, 시각 디자인 산출물(별도 작업).

## 2. 대상 사용자와 역할

중소 제조사/브랜드의 두 역할 (`product-scope-v1.md` §2):

| 역할 | 주 사용 맥락 | 주 화면 | 기기 |
|---|---|---|---|
| **오너(대표)** | 하루 현황 파악, 확인이 필요한 항목 훑기, 가벼운 검토/승인 | 대시보드, 알림, 고객 응대(읽기) | **모바일 비중 높음** |
| **온라인 판매 운영 담당자** | 문의·리뷰 응대 작업, 주문·매출 확인, 채널 연결·복구 | 고객 응대, 주문·매출, Backstage 전체 | 데스크톱 중심 |

- [현행] 기존 페르소나 문서(`sellerops_ui_reference.md` §1)는 "40–50대 제조사 CEO"를 명시했고
  타입 스케일(기본 17px, `tailwind.config.ts`)의 근거였다.
- [목표] 두 역할을 모두 지원하되 **큰 활자·저밀도 기조는 유지**한다(오너 경험 우선).

## 3. Frontstage / Backstage

`product-scope-v1.md` §1.1의 2층 구조를 프론트 IA의 최상위 원리로 삼는다.

- **Frontstage — 매일의 커머스 운영**: 대시보드 / 주문·매출 / 고객 응대(문의+리뷰) / 상품 이슈 / 리포트.
- **Backstage — 연결·수집 관리**: 채널 연결, 자격증명, 동기화 설정, 수집 이력, 기간 지정 수집,
  파일 업로드, 연결 알림·복구.
- 규칙:
  1. Frontstage가 1차 내비게이션이다. Backstage는 "설정/연결 관리" 성격의 2차 위계로 묶는다.
  2. **기존 커넥터·수집 화면은 버리지 않고 Backstage로 재배치해 재사용**한다 — `/channels`,
     채널 상세(자동 수집 관리), `/upload`, `/alerts`는 온보딩·채널 관리·복구 플로우의 부품이 된다.
  3. Frontstage 화면에는 수집 파이프라인 용어(트리거, 커서, capability 등)가 노출되지 않는다(§12).
  4. Backstage 상태(연결 장애·수집 실패)는 Frontstage에 **요약 신호**(배지·배너)로만 올라오고,
     처리 동선은 Backstage로 이어진다.

## 4. 사용자 여정

각 여정은 [현행] 상태와 [목표] 상태를 함께 기록한다. 근거 경로는 정찰 보고서(2026-07-07)와 코드.

### 4.1 가입과 워크스페이스 설정
- [현행] **가입 UI 없음.** `/login`에 데모 계정이 프리필(`frontend/src/pages/Login.tsx:8-9`).
  백엔드 `POST /api/auth/signup`(org+user 생성)은 존재하고 프론트 `api.signup`은 정의만 되고 미사용.
- [목표] 셀프서비스: **가입 → 워크스페이스/회사 설정(상호·담당자) → 채널 연결로 유도.**
  첫 파일럿은 assisted(운영자가 계정·연결을 대신 준비)를 허용하되, assisted 전용 화면을 따로
  만들지 않고 셀프서비스 플로우를 운영자가 대신 밟는 형태로 한다.
- [BE-DEP] 워크스페이스 설정 항목(조직 프로필 수정 API)은 현재 없음 — signup 파라미터(orgName)만 존재.
- 데모 프리필은 데모 모드(§13.4)에서만 유지하고 production 빌드에서 제거한다.

### 4.2 첫 채널 연결
- [현행] **Cafe24만 완결**: `/channels` 카드 → `/connect/cafe24`(몰 ID) → OAuth 동의 →
  `/connect/cafe24/result`. PENDING("연결 계속하기")·RECONNECT_REQUIRED("다시 연결하기") 재개 지원
  (`frontend/src/lib/channelConnection.ts`).
- [현행-결함] **비-Cafe24 API 채널은 막다른 길**: "연결하기" → 안내문만(`Channels.tsx` notice 분기).
  자격증명 입력 폼은 채널 상세(`/channels/:accountId`)에 있으나 **계정을 만들 UI/API가 없음**
  (`SellerAccountController`는 목록+파일채널 등록만).
- [목표] 채널 선택 → (채널별) **자동 연결(OAuth류) 또는 가이드형 키 등록**(발급처 안내 + 입력 +
  연결 확인) → 연결 완료. 연결 방식·가능 채널은 커넥터 로드맵 §4.1 현행표를 따르며, 현행표에
  없는 채널은 연결 카드를 노출하지 않거나 "미지원"으로 표기.
- [BE-DEP] **비-Cafe24 채널의 seller-account 생성 엔드포인트 신설 필요** — 이 여정의 최대 선행 조건.

### 4.3 첫 동기화
- [현행] 채널 상세의 "지금 수집하기"(수동 동기화)·"기간 지정 수집"(백필)·업로드가 존재. 결과는
  행 수 카운트로 보고.
- [목표] 연결 직후 **첫 동기화를 온보딩 단계로 안내**(무엇을 얼마나 가져왔는지 셀러 언어로 요약)
  → 스케줄·알림 설정 제안 → 대시보드 착지. `totalRows=0`은 "최신 상태(변경 없음)"로 표기(실패 아님).

### 4.4 일상 운영 (매일)
- [목표 루프] 대시보드에서 하루 요약과 "확인 필요" 항목 확인 → 고객 응대에서 문의·리뷰 처리
  (v1: 확인·분류·응답 유형 제안까지) → 주문·매출 확인 → (필요 시) 상품 이슈 검토.
  모바일에서는 이 루프의 읽기·확인 부분이 1급(§14).
- [현행 격차] 홈이 주문·매출만 표시(문의·리뷰 수치는 라이브 소스 부재로 의도적 제외 —
  `Home.tsx:10-14`). 문의·리뷰가 인박스/문의 응답/채널 상세에 분산.

### 4.5 연결 장애와 복구
- [현행] 잘 갖춰진 편: 연결 알림(`/alerts` — 유형별 안내+확인 처리), 채널 상세의 상태별 "다음 조치"
  패널(6개 상태, `ChannelDetail.tsx:115-154`), 연결 확인(auth 테스트), 자격증명 재입력, 수집 재시도.
- [목표] ① Frontstage에 장애 요약 신호(대시보드 배너·내비 배지 [현행 유지]) → ② 알림에서 원클릭으로
  해당 채널의 복구 동선 진입 [현행 유지] → ③ 복구 완료를 같은 화면에서 확인. Cafe24 외 채널의
  "다시 연결" 동선은 4.2의 [BE-DEP] 해소 후 일반화.

### 4.6 데이터 없음·부분 데이터 상태
- [현행] 빈 상태는 대체로 정직("아직 업로드된 문의/리뷰가 없습니다" + 업로드 CTA). 오류 카피가
  개발자 언어("백엔드가 실행 중인지 확인해 주세요")로 통일돼 있는 것이 문제(§13).
- [목표] 3분류를 구분해 표기한다:
  - **아직 연결 안 됨** → 채널 연결 CTA (온보딩 유도).
  - **연결됨, 데이터 0건** → "최신 상태" 또는 "수집된 데이터가 아직 없습니다" (실패 아님).
  - **일부 채널만 연결/일부 기간만 수집** → 집계 화면에 **부분 데이터 고지**(예: "네이버 기준,
    다른 채널은 연결되지 않았습니다") — 전체인 것처럼 보이는 부분 집계 금지.

## 5. 목표 정보 구조 (IA)

```
Frontstage (1차 내비게이션)
├─ 대시보드            오늘의 운영 현황 + 확인 필요 항목 (org 횡단)
├─ 주문·매출           기간·채널 필터 집계 (현행 /orders 계승)
├─ 고객 응대           문의 + 리뷰 통합 워크스페이스 (현행 /inbox + /inquiries 통합)
├─ 상품 이슈           상품별 반복 이슈 후보 (현행 /issues 계승)
└─ 리포트              수집 데이터 기반 리포트 (데이터 생기기 전까지 정직한 빈 워크스페이스)

Backstage (2차 위계 — "연결·설정")
├─ 채널 연결           카탈로그 + 연결 상태 (현행 /channels)
│   └─ 채널 상세       연결 정보·동기화 설정·수집 이력·기간 지정 수집 (현행 /channels/:accountId)
├─ 연결 알림           커넥터 알림 + 확인 처리 (현행 /alerts)
├─ 자료 업로드         파일 업로드 브리지 (현행 /upload — 1차 메뉴에서 이동)
└─ 워크스페이스 설정    조직·계정 (신규, [BE-DEP])

제외
└─ AI 검색             standalone 페이지 제거 — 향후 맥락형 "운영 메모리" 패널로만
                       (scope §5·§7-10, 별도 승인 전 구현 금지)
```

- 고객 응대 통합의 근거: 같은 데이터(문의·리뷰)가 현재 4곳(인박스, 문의 응답, 채널 상세의
  수집된 리뷰·문의, 상품 이슈)에 다른 형태로 등장해 정본 화면이 없다(정찰 F3). 통합 워크스페이스가
  정본이 되고, 채널 상세의 목록은 "이 채널에서 수집된 것" 확인용 보조 뷰로 유지한다.
- [TODO-PO] 카탈로그 노출 채널 집합 — 현행 데모 카탈로그 13채널(`frontend/src/lib/mocks.ts:76-95`)
  vs 커넥터 문서 채널 7종. v1 카드 노출 기준(연결 가능만? 요청하기 카드 존치?) 결정 필요.

## 6. 내비게이션과 모바일 내비게이션

- [현행] 데스크톱 좌측 사이드바 10개 메뉴(`Sidebar.tsx`), **`md` 미만에서 사이드바가 사라지고 대체
  내비게이션 없음** — 모바일 탐색 불가(정찰 F2, Critical).
- [목표-데스크톱] 사이드바 2그룹: Frontstage 5개 + "연결·설정" 그룹(Backstage). 연결 알림 배지는
  현행 로직(`openAlerts.tsx`) 유지.
- [목표-모바일] **하단 탭 바**: 대시보드 / 주문 / 고객 응대 / 알림 (+ "더보기"에 Backstage).
  Backstage 밀도 화면(채널 상세, 업로드)은 데스크톱 우선 — 모바일에서는 열람 가능하되 최적화
  후순위(scope §5 모바일 1급 범위).
- 이모지 아이콘은 아이콘 세트로 교체 [목표 — 시각 폴리시 슬라이스에서].

## 9. 대시보드 원칙

1. **"오늘 무엇을 확인해야 하는가"가 첫 화면의 답**이다. 확인 필요 항목(미답변 문의, 부정 리뷰,
   연결 장애, 주문 급변)이 지표 카드보다 위이거나 동급 최상단.
2. **정직한 수치 사다리**: 라이브 소스가 있는 지표만 수치로 올린다(현행 `Home.tsx` 원칙 계승).
   소스가 없으면 카드 자체를 만들지 않는다 — "0" 또는 가짜 시드로 채우지 않는다.
   지표별 편입 시점은 커넥터 현행표의 상태를 따른다.
3. **부분 데이터 고지**: 연결된 채널 기준임을 명시(4.6). "네이버 주문·매출이 연결되어 있습니다"
   같은 하드코딩 문구([현행] `Home.tsx:23`)는 연결 상태 데이터에서 파생한 동적 문구로 교체.
4. **org 횡단이 기본 단위** [BE-DEP]: 현행 attention/요약 API는 계정 단위
   (`/api/seller-accounts/{id}/…`) — 대시보드가 채널 횡단이 되려면 org 수준 집계 엔드포인트 필요.
   그 전까지는 "채널별 카드 나열"로 정직하게 구성.
5. 모바일에서 대시보드는 **읽기 전용 요약 + 알림 진입**으로 완결돼야 한다(§14).

## 11. 채널 관리(Backstage) 원칙

1. **채널 상세의 섹션 위계 재정렬**: 연결 상태·다음 조치(최상단) → 연결 정보 → 동기화 설정 →
   수집 이력 → 기간 지정 수집(고급) → 수집된 데이터 확인. [현행] "기간 지정 수집"이 "연결 상태"
   위에 있음(정찰 F7).
2. **상태 어휘 단일화**: 카탈로그 status / 계정 connectionStatus / 연결 state / run status가 셀러에게
   서로 다른 배지로 보이는 현행(정찰 F11)을 "이 채널은 지금 정상인가 + 마지막 동기화"의 한 문장
   요약으로 통합하고, 세부는 펼침으로.
3. **capability 표기는 현행표 위임**: "수집 가능 데이터" 배지·문구는 커넥터 로드맵 §4.1의 셀러 표기
   열과 4단계 규칙(부록 A — 운영 지원만 "지원")을 따른다. 프론트에 별도 진실 목록을 두지 않는다.
4. 연결 실패·만료 상태에서는 **다음 조치 1개**가 화면의 주인공(현행 NextActionPanel 계승).
5. 업로드는 "자동 연결이 어려울 때의 백업"이라는 현행 프레이밍 유지.

  선표기하지 않는다.

## 16. 가이드 연결 (Guided Connection) — 정본

채널 연결을 비기술 오너·운영자가 스스로 완주하도록 **단계별로 안내**하는 경험. 제품 원칙은
`docs/product-scope-v1.md` §1.2·§6.1, 런타임 경계는 `docs/sellerops_local_agent_runtime_adr.md`
(Runtime ADR)가 정본이며, 본 절은 그 위의 **프론트 화면·상호작용 정본**이다.

> **정직성 경계.** 이 절이 기술하는 목표 경험 중 **인앱 브라우저 프로젝션·자동 재로그인·OS
> 자격증명 저장·Windows 지원은 아직 구현되지 않았다.** 화면·문구로 구현된 것처럼 보이게 하지 않는다.
> 시각 세부(패널 폭, 버튼 라벨, 애니메이션, 코치마크 모양)는 **[UX-DECISION]** — 본 문서에서 확정하지
> 않는다.

### 16.1 목표 온보딩 경험
- 채널 선택 → SellerOps가 해당 채널의 실제 연결/발급 화면을 안내하며 **게임 튜토리얼처럼 단계별로**
  진행 → 필요한 사용자 행동(로그인·발급 클릭 등)을 짚어주고, 안전한 편의 단계는 자동 수행 →
  연결 확인 → 첫 동기화 → 대시보드 착지.
- 목표 형태는 실제 마켓/API-센터 브라우저 흐름을 **SellerOps 안에서** 보여주는 것(프로젝션). 파일럿은
  더 단순한 형태(별도 브라우저 창 + 옆의 단계 안내)로 시작할 수 있으나, **아키텍처는 인앱 프로젝션으로
  확장 가능해야 한다**(Runtime ADR).

### 16.2 프로젝션 레이아웃 (구조 원칙만; 치수는 [UX-DECISION])
- 2영역 구조: **프로젝션 뷰**(실제 브라우저 화면 투사) + **단계 패널**(현재 단계·진행·다음 행동).
- 프로젝션 뷰 위에 타깃 하이라이트(코치마크)를 얹을 수 있다 — 단, 좌표·요소 메타데이터를 프론트로
  넘기는 것은 sanitized 계약의 **로컬 신뢰 채널 예외**가 선결이다(§16.9, Runtime ADR, [PO-DECISION]).
- 파일럿 단계에서 프로젝션이 없으면 단계 패널만으로 별도 창을 안내한다(동일 단계 정의 재사용).

### 16.3 단계 패널·진행 동작
- 각 단계: 제목 · 짧은 설명 · "지금 할 일"(사용자 행동) 또는 "SellerOps가 진행 중"(자동) 표시 ·
  완료 조건. 진행 표시(예: n/총 단계)는 구조 요구이며 **표현 방식은 [UX-DECISION]**.
- 단계 정의는 **채널별 재사용 가능한 flow 정의**에서 온다(다채널 확장 대비 — Connector Roadmap
  "가이드 셋업 방식" 열, Runtime ADR의 flow 정의 경계).

### 16.4 사용자 행동 vs SellerOps 행동 규칙
- **SellerOps 자동(안전·결정적 편의 단계)**: 페이지 열기·이동, 입력란으로 스크롤, 붙여넣기 위치 안내,
  연결 테스트 실행, 다음 단계로 진행.
- **사용자 통제(항상)**: 계정/스토어 선택, 권한·동의, 발급 클릭, 법적 의미 있는 결정, 의도가
  불확실한 판단. 감독형 클릭이 필요한 경우 **정확히 1개**만, 사용자 승인 후(현행 감독형 클릭 원칙
  계승 — collector `review-usage-confirm.ts`).

### 16.5 로그인·2FA·CAPTCHA 처리
- **절대 자동화/우회하지 않는다.** 인증이 필요하면 단계 패널이 "직접 로그인/인증해 주세요"로 사람에게
  넘기고, 완료를 감지하면 다음 단계로 진행한다. 에이전트는 자격증명을 입력하지 않는다.

### 16.6 실패·복구·재개
- 단계 실패(요소 못 찾음·페이지 변경·타임아웃)는 **해당 단계에서 멈추고** 재시도/직접 진행 안내를
  제시한다(무한 자동 재시도 금지).
- 세션 만료·계정 드리프트 시: 전용 프로필 세션 보존 + 사람 재로그인 요청(§16.7 폴백). 중단된 작업은
  재개 가능해야 한다(자동 재로그인이 붙으면 이어서, 아니면 사람 개입 후).

### 16.7 로컬 에이전트 상태 (offline / 미설치 / 미페어링)
가이드 연결은 로컬 에이전트를 전제로 하므로, 프론트는 아래 상태를 **명시적으로** 표시한다:
- **미설치**: 로컬 에이전트 설치 안내(설치 패키지·절차는 [BE/AGENT-DEP], 현재 미구현).
- **미페어링**: 프론트-에이전트 페어링 유도(페어링 계약은 Runtime ADR, 미구현).
- **offline(설치·페어링됨, 실행 안 됨)**: "로컬 에이전트가 실행 중이 아닙니다" + 실행 안내.
- **정상(페어링+실행)**: 실시간 단계 상태 수신.
> 이 상태들의 이벤트/전송 채널은 **현재 미구현**(정찰 §3: 프론트-에이전트 통신 부재). 화면은 상태
> 개념을 정의하되, 실동작은 Local Agent Bridge 슬라이스(§17-B G1)에 의존한다.

### 16.8 반응형
- 가이드 연결(프로젝션+발급 흐름)은 **데스크톱 우선**(로컬 에이전트가 데스크톱 런타임). 모바일에서는
  진행 현황·완료 확인 정도의 열람만 지원하고, 실제 연결 작업은 데스크톱으로 안내(§14 모바일 범위와 정합).

### 16.9 보안·프라이버시 규칙
- **영속 로그 금지 대상**(Browser Projection 원칙 계승): 스크린샷·프레임·키 입력·URL·자격증명·
  페이지 본문을 영속 로그에 남기지 않는다. collector의 sanitized 계약(enum/boolean/coarse bucket/
  16-hex 해시)과 일치.
- 프로젝션 스트림·입력 릴레이는 **로컬 신뢰 채널** 전제(전송·비영속·비로깅). 좌표/URL/요소
  메타데이터를 프론트로 넘기는 예외는 **명시적 정책 결정** 후에만(§16.2, [PO-DECISION]).
- 동의 3종(자동 로그인 · 자격증명 저장 · 마켓 권한)은 **분리된 명시적 동의**로 각각 받는다
  (`product-scope-v1.md` §1.2). Device Vault·자동 입력은 미구현 — UI가 있는 것처럼 표기 금지.

### 16.10 NAVER 프로토타입 흐름과 완료 기준
- **첫 가이드 연결 프로토타입: NAVER 커머스 API 애플리케이션 발급 + 연결.**
- **파일럿 운영 모델**: assisted 온보딩(제품 오너가 관찰하는 가운데 진행).
- **완료 기준(6단계)**: ① SellerOps에서 NAVER API 센터 흐름 열기 → ② 앱 발급을 사용자에게 안내 →
  ③ Client ID·Secret을 안전하게 등록 → ④ 연결 테스트 통과 → ⑤ 첫 실주문 데이터 수집 → ⑥ SellerOps에
  수집 결과 표시.
- **현행 근거**: 주문 수집은 `POST …/credentials`(Vault 저장) → `test-connection` → 수동 sync →
  대시보드로 이미 존재(NAVER ORDER_SUMMARY 라이브 1회 검증 — Connector Roadmap §4.1). 가이드 연결은
  이 경로에 **단계 안내·in-app 발급 화면**을 얹는 것이다.
- **경계**: 이 흐름은 **셀러 소유 NAVER 앱 발급 파일럿 경로**다. 미래 SellerOps **솔루션-제공자
  OAuth 연동 모델로 문서화하지 않는다**(`product-scope-v1.md` §6.1).

### 16.11 첫 파일럿 범위와 명시적 제외
- **범위**: NAVER 6단계 완료 기준(§16.10)을 assisted로 1회 통과.
- **제외**: 인앱 프로젝션 없이도 파일럿 가능(별도 창 + 단계 패널); 자동 재로그인·Device Vault·
  Windows·클라우드·다채널 flow 자동화·자동 발급 클릭은 **제외**. 인증 우회·계정 선택 자동화 **영구 제외**.

## 17. 구현 슬라이스와 FE/BE 의존성

작은 PR 규율(CLAUDE.md) 준수. 순서는 권장이며 각 슬라이스는 독립 머지 가능해야 한다.
**본 문서는 계획이다 — 코드 착수는 슬라이스별 승인으로.** Product Shell(§17-A)과 가이드 연결
인프라(§17-B)는 **분리된 트랙**이며, 승인된 시퀀싱은 아래를 따른다.

클라우드 관리형 런타임.

### 17.1 API 계약 방침

- [현행] `frontend/src/lib/types.ts`(백엔드 DTO 수기 미러)와 `apiClient.ts`가 사실상의 FE 계약이다.
  이는 **임시 미러이며 장기 source of truth가 아니다.**
- [목표] 계약의 정본은 **백엔드 OpenAPI 명세**로 한다. 프론트 타입과 mock은 그 계약에서
  **생성하거나 계약에 대해 검증**하는 구조로 이행한다(springdoc 등 도입은 별도 BE 슬라이스).
- 이행 전까지의 규칙: DTO 변경은 백엔드 PR에서 `types.ts` 동기 수정을 동반하고, 신규 화면은
  `types.ts`에 없는 필드를 임의 가정하지 않는다.
