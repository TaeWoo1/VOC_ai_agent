# Planner Model Benchmark v1

**2026-09-01 · HEAD `bd547be7` · 측정만, 제품 변경 0.**

`docs/agent_responsiveness_v1.md` §7이 「하지 않고 보고한 것」의 첫 줄로 남긴 질문에 답한다 —
**플래너 모델 교체는 남은 가장 큰 지렛대이고 product-owner 결정이다.** 그 문서는 토큰-시간 관계로
「방출 속도 2배 모델이면 중앙값 ≈1.7s」라고 **외삽**했고, 외삽은 측정이 아니라고 스스로 적었다.
이 문서는 그 외삽을 실제 실행으로 대체한다.

**결론 먼저: 기본 플래너 모델을 바꾸지 않았다.** 어떤 후보도 「correctness를 유지하면서 latency와
cost를 함께 낮춘다」를 만족하지 못했고, 가장 강한 후보(`gpt-5.6-luna` @ `low`)는 정확도와 비용을
개선하는 대신 **지연을 35% 늘리고 제품의 중심 동작인 「답변 초안 준비」를 회귀시킨다**. 애매하면
바꾸지 않는다.

---

## 0. 무엇을 측정했고 무엇을 측정하지 않았는가

측정한 것은 **플래너 capability 하나**(`sellerops.agent.plan.*`)다. Draft·Judge·Triage capability의
모델은 **건드리지 않았고**, 모든 arm에서 동일하다. 프롬프트(`agent-plan-prompt/v10`), plan 스키마,
tool catalogue, 검증기, repair 규칙, 그리고 결정론 lane 전부 **바이트 단위로 동일**하다 — arm 사이에서
움직인 것은 `SELLEROPS_AGENT_PLAN_MODEL`과 `SELLEROPS_AGENT_PLAN_REASONING_EFFORT` 둘뿐이고, 매 arm은
백엔드를 **재기동해서** 그 값을 프로세스 환경에서 다시 읽어 확인한 뒤 시작했다(장수 dev 프로세스는
버전 핀이다).

측정하지 않은 것: 벤더의 다른 모델들, 다른 프롬프트, 다른 스키마, 다른 tool 집합. 이 벤치마크는
**모델 선택**에 대한 것이지 플래너 설계에 대한 것이 아니다.

### 0-1. `reasoning_effort` 어휘는 모델 사이에서 이식되지 않는다

교체를 한 줄 변경이라고 생각했다면 그것부터 틀렸다. API에 직접 물어본 결과:

| 모델 | `minimal` | `none` | `low` |
|---|---|---|---|
| `gpt-5-2025-08-07` (현재 기본값) | ✅ | ❌ 400 | ✅ |
| `gpt-5.6-luna` | ❌ 400 | ✅ | ✅ |
| `gpt-5.4-mini` | ❌ 400 | ✅ | ✅ |

> `Unsupported value: 'reasoning_effort' does not support 'minimal' with this model.
>  Supported values are: 'none', 'low', 'medium', 'high', and 'xhigh'.`

즉 **현재 shipped 기본값 `reasoning-effort: minimal`은 두 후보 모두에서 400을 받는다.** 모델을 바꾸면
effort도 함께 바꿔야 하고, 그렇지 않으면 모든 플래너 호출이 실패한다(= 모든 자유 문장 turn이 실패).
「같은 reasoning 설정으로 비교하라」는 요구는 그래서 **이름이 아니라 의미**로 만족시켰다 — baseline의
`minimal`과 후보의 `none`은 둘 다 **내부 reasoning 토큰 0**을 내는 설정이며(프로브로 확인), 이것이
공정한 짝이다. repair escalation은 모든 arm에서 한 단계 위로 두었다.

## 1. 고정 eval set

**53 문장 · 16 그룹**(그룹 하나 = 대화 하나, 순서가 의미를 만든다). PO QA와 회귀에서 실제로 깨졌던
문장과 그 paraphrase를 포함한다. 파일: 재현 가능한 형태로 scratchpad에 두었고, 각 turn은 **기대값**을
함께 든다.

| 그룹 | 무엇을 가르는가 |
|---|---|
| G01 | new list vs visible-set refine (`conversation_core_chat_ux_v1` §9 회귀) |
| G02 | subject term · NEW_SUBJECT (`conversation_ux_v2` §1 회귀) |
| G03 | channel × status × order × limit × 기간 조합, count |
| G04 | ordinal select → inspect → analyze → prepare |
| G05 | analyze vs priority (`urgency`) |
| G06 | ambiguous reference (anchor 없음 · 집합 위 대명사) |
| G07 | priorContext multi-turn chain |
| G08 | 운영 정책 3종 retrieval + 복합 draft |
| G09 | unsupported / 승인 경계 |
| G10 | 리뷰 · 반복 문제 심층 조사 |
| G11 | 주문 리포트 + refine |
| G12 | topic filter · 결정론 refine chain |
| G13 | paraphrase (목록 · 미답변 · 우선순위) |
| G14 | 상품 lane |
| G15 | label select → prepare → tone revision |
| G16 | 지식 공백 · 취소 · anchor 뒤 org 질문 |

**채점은 문장이 아니라 제품 결과로 한다.** 기대값은 코퍼스가 답을 결정하는 곳에서는 **id와 닫힌
토큰**으로 적힌다 — 어떤 문의 행이 어떤 순서로 그려졌는가(`rowIds`), 채널이 전부 맞는가, 초안이
**어느 문의에** 붙었는가, 결정론 lane이 모델을 부르지 않았는가(`llm: 0`). 문장 내용을 보는 것은
판매자 자신의 숫자가 답에 실려야 하는 정책 질문뿐이다(「7일」·「30일」·「오후 2시」).

코퍼스는 **일회용 org**(제품 자신의 signup으로 생성)에 고정 시드: 문의 15건(미답변 12 · 답변 3,
NAVER 8 · 카페24 7), 리뷰 14건(부정 8), 리뷰 이슈 2건(포장 파손 근거 4 · 설명 부족 근거 2), 상품 3개,
운영 정책 3건(배송·교환반품·현금영수증), 상품 지식 2건, 주문 일별 집계 60행. 실제 판매자 데이터 **0**.

## 3. 대표 failure — 숫자가 아니라 무엇이 틀렸는가

**모든 arm이 틀리는 10개 turn은 모델이 아니라 이 제품의 성질이다**(G02.2 · G03.4 · G07.3 · G08.4 ·
G10.1 · G12.4 · G14.1 · G14.2 · G15.2 · G16.1). 그 turn들을 빼고 봐야 모델 사이의 차이가 보인다.
대표적으로 **기간 조건이 읽기 인자로 내려가지 않는다** — 「최근 3일 안에 들어온 문의만 보여줘」에
다섯 arm 전부 15건 전체를 그렸다. 이것은 다음 패키지의 일이다.

### `gpt-5.4-mini` @none — 심층 조사에서 도구를 하나도 부르지 않는다

「최근에 반복해서 문제가 생기는 상품이 있어?」 (제품 문서가 스스로 flagship으로 쓰는 문장)

| | tools | 답 |
|---|---|---|
| baseline | `search_review_issues` + `get_review_issue_evidence_summary` ×2 | 「…논슬립 주방 매트 45x120에 리뷰 문제 근거가 4건 … 가장 많은 것은 "포장 파손" 4건」 |
| luna @none | 같음 | 같음 |
| **mini @none** | **`[]`** | 「리뷰 신호는 이번 조사 계획에 포함되지 않았습니다.」 |

**두 pass 모두** 같았다. 노이즈가 아니라 계획 능력의 구멍이다.

### `gpt-5.6-luna` @none — 분명한 문장에서 계획 자체를 실패한다

「논슬립 주방 매트 리뷰는 어때?」 → `FAILED` 「요청을 어떻게 조사할지 계획하지 못했습니다.」 (1/2)
「채널별로 나눠서 보여줘」 → `FAILED` (1/2). baseline은 212 turn에서 hard FAILED가 **0**이다.

### `gpt-5.6-luna` @low — 가장 강한 후보이고, 그래도 초안 chain을 회귀시킨다

**baseline보다 나은 곳 5개**(4 pass 기준):

| turn | 문장 | baseline | luna @low |
|---|---|---|---|
| G06.1 | 「그거 어떻게 처리하지?」 (anchor 없음) | **0/4** — CHART·ORDER_SUMMARY·CHECKLIST·INQUIRY_LIST로 대시보드를 지어냄 | **4/4** — 「무엇을 확인할지 조금 더 구체적으로 알려주세요」 |
| G06.3 | 「미답변 문의 보여줘」 (평범한 새 목록) | **0/4** — 「방금 본 문의 중 답변 안 한 문의는 **없습니다**」 (앞 turn이 지어낸 집합 안에서 좁힘) | **4/4** — 12건 |
| G05.3 · G12.2 · G12.3 | 우선순위 paraphrase · 목록 · 결정론 채널 refine | 2/4 · 1/4 · 1/4 | 4/4 · 4/4 · 4/4 |

G06.1 → G06.3은 **한 사슬**이고, 이 제품이 두 번 닫은 바로 그 결함(new-list scope contamination)이
baseline에서 **4 pass 전부** 재현된다.

**baseline보다 나쁜 곳 1개**, 그런데 그것이 제품의 중심 동작이다:

| turn | 문장 | baseline | luna @low |
|---|---|---|---|
| G15.3 | 「답변 초안 만들어줘」 (앞 turn에서 문의 하나를 지목한 뒤) | **4/4** — DRAFT | **2/4** — 「어떤 문의의 답변을 준비할지 알려주세요」 |

원인은 초안 능력이 아니라 **앞 turn의 범위 해석**이다: luna @low는 「배송이 너무 늦습니다 이거
보여줘」를 org 범위의 새 주제 목록으로 읽어 2건(미답변 1 + 답변함 1)을 그렸고, 그래서 다음 문장에서
대상이 하나로 좁혀지지 않았다. baseline은 매번 1건으로 좁혀 초안을 만들었다.

luna @low의 hard FAILED 4건은 **전부 모든 arm이 이미 틀리는 turn**(G14.2 ×3 · G03.4)에서 나왔다 —
같은 오답을 더 거칠게 말한 것이지 새로 못하게 된 것은 아니다.

### `gpt-5.4-mini` @low — 지연은 baseline과 같아지고, 회귀는 늘어난다

정확도 75.5%로 baseline보다 높지만 회귀가 **3개**다: G15.3 초안 준비 **0/2**, G15.4 말투 다듬기
**0/2**, G16.3 anchor 뒤 org 질문 1/2. hard FAILED **6/106 (5.7%)**. p50은 3,120ms로 baseline과
사실상 동일하다(≈ −0.7%) — 즉 `low`에서는 mini의 속도 이점이 사라진다.

## 4. 판정

| 후보 | correctness 유지? | latency | cost |
|---|---|---|---|
| luna @none | ❌ (−0.5pp, hard FAILED 5/106, 분명한 문장에서 계획 실패) | ✅ −16% | ✅ −86% |
| luna @low | ⚠️ 총량은 +6.6pp이나 **초안 준비 회귀** | ❌ **+35%** | ✅ −84% |
| mini @none | ❌ **심층 조사에서 도구 0** (재현됨) | ✅ −42% | ✅ −47% |
| mini @low | ❌ 회귀 3개 · hard FAILED 5.7% | ≈ 동일 | ✅ −37% |

**어떤 후보도 「correctness 유지 + latency·cost 하락」을 함께 만족하지 못한다.** 가장 좋은 후보인
luna @low는 정확도와 비용을 크게 개선하지만 직전 패키지가 되찾은 지연을 3.1s → 4.2s로 되돌리고,
판매자가 가장 자주 누르는 동작에서 회귀한다.

⇒ **플래너 기본값 무변경.** `gpt-5-2025-08-07` @ `minimal` 유지.

## 5. product-owner 결정으로 올리는 것

**`gpt-5.6-luna` @ `low`로 교체할 것인가.** 저장소가 대신 답할 수 없는 교환이기 때문이다:

- 얻는 것: 정확도 **73.1% → 79.7%**(212 turn 기준), 플래너 호출 비용 **−84%**(100회당 $1.007 →
  $0.159), turn p95 **10.1s → 9.0s**, 그리고 이 제품이 반복해서 싸운 **new-list scope 오염이 사라짐**.
- 잃는 것: 플래너 p50 **3.1s → 4.2s (+35%)**, 「답변 초안 만들어줘」가 4/4에서 2/4로.

이 벤치마크는 **일회용 org 하나 · 고정 코퍼스 하나 · 한 대의 기계**에서 나온 수치다. 교체를 실제로
결정한다면 파일럿 org의 실제 코퍼스에서 같은 eval set을 한 번 더 돌리는 것이 옳다.

## 6. 정직하게 적어 두는 것

- **비용 단가는 벤더 페이지에서 읽은 외부 사실**이고 저장소가 검증할 수 없다. 토큰 수는 벤더가
  응답에 실어 보낸 자신의 숫자이고, 시간은 transport가 잰 자신의 시계다.
- **모델 교체는 effort 값 교체를 동반해야 한다**(§0-1). 모델만 바꾸면 플래너는 400으로 전멸한다.
- 벤치마크 실행 중 **판매자 일일 AI 예산**(`daily-runs-per-org`, 기본 200)을 모든 arm에 대해 동일하게
  올렸다. 처음 시도에서는 그것을 하지 않아 baseline 106 turn 중 **64개가 「오늘 사용할 수 있는 AI
  분석 횟수를 모두 썼습니다」**를 측정하고 있었다 — 모델의 행동이 아니라 예산의 행동이다. 제품
  코드는 그대로다.
- **마켓플레이스 호출 0 · 마켓플레이스 WRITE 0 · 실제 판매자 데이터 0 · 마이그레이션 0 ·
  제품 소스 변경 0.** 모델 호출은 이 벤치마크가 지불한 플래너 638회와 초안 소수.
- 이 문서는 `docs/agent_responsiveness_v1.md` §7의 「모델 교체 = 남은 가장 큰 지렛대」를 **닫지
  않고 값을 채운다**. 그 항목은 여전히 열린 product-owner 결정이며, 이제 외삽이 아니라 측정 위에 있다.
