## §0 먼저 본 것 — 7개 제품의 interaction pattern (구현 전 bounded 조사)

브랜딩·픽셀은 복제하지 않았다. 가져온 것은 **원리**뿐이고, 각 원리가 이 저장소의 어떤 결함에
대응하는지만 적는다.

| 제품 | 가져온 pattern | reviewnary 적용 |
|---|---|---|
| **Atlassian Rovo** | 채팅 패널이 열린 화면의 객체를 자동 scope로 잡는다 · reasoning trace를 실시간으로 흘린다 | §1 ContextBar · §3 진행 단계 |
| **Notion Agent** | 기본 scope가 **커서/선택**을 따라가고, 결과가 대화 안에서 조작 가능한 객체로 렌더된다 | §1 (선택이 곧 scope) · §2 (브리핑이 클릭 가능한 행) |
| **Linear (Triage Intelligence)** | 제안에는 **한 번의 클릭으로 볼 수 있는 이유**가 붙는다 | 이미 있던 것(순위 기준 문장·`waitingDays`)을 §2가 홈에서도 쓴다 |
| **Asana Dash** | 매일의 브리핑은 상태 dump가 아니라 **사람이 결정할 지점**에서 끝난다 | §2 홈 브리핑 |
| **Devin** | 계획이 **검토 가능한 산출물**이고, 근거(코드 인용)에 묶여 있다 | §3 — 다만 이 저장소에서 정직하게 할 수 있는 것은 **실제 도달한 단계**뿐 |
| **Sierra Explorer** | insight → 근거 → **다음 행동으로의 handoff**가 한 카드에서 닫힌다 | 기존 초안 카드가 이미 그 모양 · §5가 중복만 걷어냄 |
| **Glean** | 인용은 hover로 싸게 확인하고, click은 원문으로 나가는 **두 단계** | 기존 `근거` disclosure 유지 |

**수렴점 중 이 저장소에 없던 단 하나**: 「에이전트가 지금 보고 있는 객체를 이름으로 말한다」.
Rovo·Notion·Linear가 모두 하는 그것이, 여기서는 **상태로는 존재하는데 화면에 없었다**.

## §1 (본체) 현재 작업 대상을 눈으로 보여준다

**결함.** 행을 클릭하면 대화가 그 문의에 anchor된다 — 런타임이 선택을 영속하고, 다음
「답변 준비해줘」가 그것에 작용하고, 지식 공백 질문도 그것에 대해 나간다. **전부 이미 참이었고 그중
어느 것도 화면에 없었다.** 유일한 피드백은 행 자체의 tint였고 그것은 스크롤되어 사라진다. 그래서 세 턴
뒤 「현금영수증 발행 기준이 필요해요」라는 질문 앞에 선 판매자는 **그게 어느 문의에 대한 질문인지 알
방법이 없었고**, 「이 문의」는 믿어야 하는 단어였다.

상태는 있었다 — `WorkingSetView.selectedInquiry`, `ActiveTask`. **그 위에 서 있는 것이 없었다**
(프론트 전체에서 `activeTask` 참조 0, `workingSet` 참조는 행 하이라이트 하나).

**`ContextBar`** — transcript와 입력 상자 **사이**에 한 줄. 판매자가 무엇을 칠지 정할 때 눈이 있는 자리이고,
페이지 맨 위의 배지는 이미 스크롤해 지나간 사실이기 때문이다.

- **ANCHOR**: 객체의 이름 · 어디서 왔는지 · 진행 중인 단계 · 「해제」
- **SET**: 화면에 있는 집합을 판매자 자신의 낱말로 (`'현금영수증' 관련 · 답변 필요 · 2건`) · 해제 불가
  (집합은 다른 것을 물어서 떠난다)

**이름은 어디서 오는가 — 새 상태가 아니다.** anchor는 계약상 id와 닫힌 토큰뿐이다(저장된 대화가 고객이
쓴 문장의 두 번째 사본을 쌓아서는 안 된다). 그래서 라벨은 **스레드가 이미 그린 artifact**에서 되찾는다 —
행의 제목은 영속되는 artifact의 일부라 **새로고침을 넘긴다**. 아무것도 fetch하지 않고, 캐시하지 않고,
transcript가 anchor를 이름 지을 수 없으면 지어내는 대신 「선택한 문의」라고 정직하게 말한다.

**절대 보이지 않는 것**: 고객 본문, id, phase, `activeTask` 토큰, 필터 enum 이름.

**`INSPECT`에는 단어를 주지 않는다.** 객체를 보여주는 것 자체가 inspection이고, 옆에 「보는 중」을 붙이면
같은 사실 두 번이다. 무언가를 **바꾸는** 단계만 단어를 얻는다(답변 준비 중 · 말투 다듬는 중 ·
답변 기준 확인 중 · 보내기 확인 중).

### §1-A 해제 — 같은 계약, 반대 방향

**볼 수 있게 된 상태는 떠날 수 있어야 한다.** 그렇지 않으면 이 바는 사실을 보고만 하고 바꿀 방법을 주지
않는다. `StartTurnRequest.select`가 `{ kind: "CLEAR" }`를 받는다 — 클릭이 지나는 **바로 그 seam**이고,
anchor와 진행 중 task를 떨어뜨리고 **그 외에는 아무것도 건드리지 않는다**: 집합은 화면에 그대로,
transcript에 추가 0, 읽기 0, 모델 0, id 없음(떨어뜨릴 anchor는 언제나 하나뿐).

프론트는 **낙관적으로 지우지 않는다**. 실패하면 바는 런타임이 여전히 들고 있는 것을 계속 보여준다 —
「해제됐다」고 말해 놓고 다음 턴이 여전히 anchor되어 있는 것이 이 바가 없애려는 바로 그 결함이다.

### §1-B 이 테스트가 찾아낸 더 오래된 결함

CLEAR 테스트를 쓰다가 **작업 큐 행을 클릭하면 집합이 그 한 줄로 무너지는 것**을 발견했다.
집합은 두 identity 중 **하나**로 색인되고 어느 쪽인지는 그것을 만든 읽기가 정한다 — ROWS 목록은 inquiry
id, 작업 큐 목록은 work-item id (`ids: bounded(rows ? … : workItemIds)`). 그런데 `anchoredSet`은 inquiry
id로만 대조하고 있었다. 그래서 작업 큐에서 첫 행을 클릭한 뒤의 「세 번째 거」·「그중 네이버만」은 **1건짜리
집합** 위에서 돌았다. 행은 두 id를 다 들고 있으므로 **둘 중 하나로 알아본다**.

## §2 홈은 세는 것이 아니라 **이름을 부른다** (Asana Dash)

**결함(실측).** 인사말이 12를 말하고, 숫자 줄이 「현재 미답변 문의 12건」을 말하고, 오프너 턴이
「답변을 기다리는 문의 12건 →」이라는 링크를 그렸다 — **같은 숫자 세 번**, 그리고 판매자는 그 12건이
**무엇인지** 여전히 몰랐다. 숫자로 끝나는 브리핑은 채팅 말풍선을 입은 대시보드 행이다.

이제 브리핑은 **실제 행**으로 끝난다 — `GET /api/inquiries/rows?status=UNANSWERED&order=OLDEST&limit=3`
한 번(대화의 「최근 문의」가 쓰는 **바로 그 읽기**), 고객이 쓴 문장·채널·상품·경과 시간이 붙은 세 행이고,
누르면 대화가 그 문의에 anchor된다(→ §1). 숫자는 **한 번**, 그 세 행이 왜 위에 있는지의 이유로서 말한다.

- 읽기가 실패하면(`null`) 기존 count 줄로 되돌아간다 — 숫자만 말할 수 있는 브리핑이 행을 지어내는
  브리핑보다 낫다.
- 행을 이름 지었으면 「답변 안 한 문의 보여줘」 칩은 **그리지 않는다**. 이름 붙은 행이 곧 다음 행동이고,
  그 아래에서 같은 목록을 다시 요청하는 칩은 같은 동작 두 번이다.
- 숫자 줄은 브리핑이 그 수를 말할 때 **미답변 항목을 뺀다**(§5). 나머지 둘은 브리핑에 없으므로 남는다.

## §3 조사 중에는 실제로 도달한 단계만 (Devin · Rovo)

진행 표시는 **시간 순서**가 된다 — 끝난 것이 위, 지금 하는 것이 아래. 이전에는 최신 줄이 맨 위이고 끝난
것들이 그 아래여서, 옆의 경과 시계와 **반대 방향**으로 읽혔다.

**여기서 정직하게 할 수 있는 것의 한계를 적어 둔다.** Devin은 계획을 검토 가능한 산출물로 보여준다.
이 저장소의 플래너 호출은 **블로킹 HTTP 한 번**이고 계획은 답과 함께 도착하므로, 그 20~30초 동안 화면이
가진 진짜 사실은 「요청을 이해하고 있습니다」와 **측정된 시계**뿐이다. 없는 단계를 그리지 않는다. 계획이
선 뒤에는 실제 단계가 흐른다 — 라이브 실측: `요청을 이해하고 있습니다 → 무엇을 확인할지 정했습니다 →
문의를 확인하고 있습니다 → 확인한 내용을 검토하고 있습니다`.

## §4 질문한 쪽이 무엇을 원하는지 입력 상자가 말한다 (Notion: scope는 커서를 따른다)

지식 공백 질문은 **판매자가 답을 타이핑하는 것**으로 끝나는데, 커서 바로 위의 「무엇이든 물어보세요」가
그 사실을 말하지 않는 유일한 자리였다. `activeTask === "CAPTURE_KNOWLEDGE"`인 동안 placeholder는
**「답변 기준을 여기에 적어 주세요」**가 된다. 새 상태 0 — 이미 영속되던 task를 읽을 뿐이다.

## §5 한 사실은 한 번만 — 라이브에서 관측된 중복만

| 어디 | 무엇이 두 번 | 어떻게 닫았나 |
|---|---|---|
| 문의 행(펼침) | 미리보기 한 줄이 바로 아래 본문의 첫 줄과 **글자 그대로 동일** | 펼쳐진 동안 미리보기를 그리지 않는다 |
| 문의 목록(ROWS) | `답변 필요 1 · 답변함 1 · 답변 필요 1` — 헤더 셋이 같은 두 가지를 이름 짓고 각각 1을 센다 | 라벨이 반복되면 헤더를 그리지 않는다(모든 행이 이미 자기 상태를 첫 단어로 말한다). 진짜로 묶인 목록은 헤더와 개수를 유지 |
| 지식 저장 카드 | 「저장한 기준으로 답변 초안을 다시 준비했습니다」가 턴 문장·카드·바로 아래 초안 카드까지 **세 번** | grounded 재초안에서는 카드 줄을 그리지 않는다. 턴 문장이 다루지 **않는** 결과(`DRAFT_STILL_GAP` 등)는 자기 줄을 유지 |
| 홈 | 미답변 수가 숫자 줄과 브리핑에 각각 | 브리핑이 이름을 부르면 숫자 줄에서 뺀다 |

### §5-A 라이브가 찾은 진짜 버그 하나

`Encountered two children with the same key: UNANSWERED` — ROWS 목록은 판매자의 **순서**를 지키므로
그룹이 연속 구간이고, 같은 `key`가 정당하게 여러 번 나온다. React는 두 형제가 같은 노드라고 들었고 행을
누락하거나 복제할 수 있다고 경고하고 있었다. **판매자의 일 목록은 그런 일이 일어나도 되는 마지막
자리다.** 위치까지 포함해 키를 잡았다. (수정 후 콘솔 오류 **0**.)

## §7 고치지 않고 보고하는 것

1. **플래너 대기 20~30초 동안 화면이 가진 사실은 시계뿐이다.** 단계별 진행에는 새 프로토콜(id-first
   start 또는 SSE)이 필요하고, 없는 단계를 애니메이션하지 않기로 한 결정은 유지한다.
2. **제안 칩은 여전히 working set만 따른다** — 리뷰/상품에 대한 org 범위 답변 아래에서도 직전 문의
   집합의 칩이 그려진다. 관측됐고 이번 패키지 범위 밖.
3. **`ContextBar`는 문의 anchor만 이름 짓는다.** `selectedInquiry`가 대화가 가진 유일한 단일 객체 anchor이고,
   상품·리뷰 anchor는 계약에 없다. SET은 다섯 종류 모두 설명한다.
4. **새로고침 뒤 목록 행은 제목만 남는다**(snippet은 의도적으로 영속되지 않는다 — Conversation UX v2 §7).
   바의 라벨은 제목에서 오므로 영향받지 않는다.
5. **홈 브리핑은 읽기를 하나 더 한다**(org 범위 READ 1회). 실패는 조용하고 count 줄로 되돌아간다.
