# Answer Applicability v1 — 근거가 검색됐다는 것과, 그 근거를 이 질문에 쓸 수 있다는 것

*2026-08-26 · `backend/` + `frontend/` · 마켓플레이스 호출 0 · DB 변경 0 · 새 마이그레이션 0*

## 0. 무엇이 잘못됐는지부터 — 그리고 무엇은 잘못되지 않았는지

2026-08-26 NAVER 라이브 증명(`docs/evidence/naver_inquiry_answer_live_proof_v1.md`)에서 고객이 물었다:

> 안녕하세요. 전선이 몇 가닥까지 들어가나요?

AI 초안(v1, `MODEL`):

> 문의 주신 제품에는 **일반 가전 전선 기준으로 3~4가닥**이 여유 있게 들어갑니다.

판매자는 이 초안을 승인하지 않고 고쳐 썼다 — 이 상품은 여러 규격으로 팔리고, 규격마다 수용 가능한
전선 개수가 다르기 때문이다.

**감사 결과, 흔히 예상할 법한 원인 셋은 모두 아니었다.**

| 의심 | 실제 |
|---|---|
| 모델이 수치를 지어냈다 | **아니다.** 저 문장은 판매자 자신이 등록한 FAQ에 있는 Q&A를 그대로 옮긴 것이다 |
| 검색이 엉뚱한 문서를 가져왔다 | **아니다.** 가져온 chunk에 「Q. 몇 가닥까지 들어가나요?」가 그대로 들어 있다 |
| 모델이 근거의 한정어를 떼어냈다 | **아니다.** 「일반 가전 전선 기준으로」를 그대로 보존했다 |

검색은 맞았고, 인용도 맞았고, 답은 여전히 틀렸다. **결함은 grounding이 아니라 applicability다** —
판매자의 FAQ 자체가 규격을 구분하지 않고 상품 단위로 쓰여 있었고, 시스템에는 「이 질문의 답은 옵션에
따라 달라진다」는 사실을 담을 자리가 아예 없었다. 근거가 돌아오면 단정할 수 있는 근거였다.

이 문서는 그 자리를 만든다. **온톨로지도, variant engine도, 새 스키마도 만들지 않는다.**

## 1. 감사 — 오늘 우리가 실제로 가진 것

| 물음 | 답 (repository-verified) |
|---|---|
| FAQ 「3~4가닥」의 scope | `product_knowledge_sources` → `product_id`. **variant 칸이 없다.** 상품 지식은 언제나 상품 단위다 |
| 문의에 옵션/variant 정보가 있는가 | **없다.** `Inquiry` 엔티티에 옵션 필드가 없고, NAVER 상품 문의 응답에도 없다 |
| 우리가 가진 variant 데이터 | `product_variants` 405행, **전부 `COUPANG:SELLER_PRODUCTS:v1`**. 이 상품에는 **0행** |
| retriever가 상품 지식과 variant 사실을 구분하는가 | **하지 않는다.** `ScopedPassage`는 lane(상품/정책/과거답변)만 구분한다 |
| composer가 적용 가능성을 검사하는가 | **하지 않았다.** 근거가 있으면 모델에 넘겼다 |

그래서 「정확한 variant를 확정할 수 없다」는 이 상품에서 추측이 아니라 **우리가 가진 것에 대한 서술**이고,
NAVER에서는 오늘 언제나 참이다.

## 2. v1 safety contract

`SpecApplicability`가 질문 하나를 셋 중 하나로 분류한다. 결정론적이고, 모델 호출이 없고, 시계를 읽지
않는다.

| 상태 | 뜻 | 드래프터가 받는 줄 |
|---|---|---|
| `NOT_VARIANT_SENSITIVE` | 답이 옵션에 따라 달라지지 않는다 (부착 방법, 반품 규정) | `(해당 없음)` |
| `VARIANT_UNRESOLVED` | 달라질 수 있고, 어떤 규격인지 확정되지 않았다 | 「…어떤 규격인지 확정되지 않았습니다」 |
| `VARIANT_NAMED` | 달라질 수 있고, 고객이 이 상품이 파는 규격 하나를 밝혔다 | 「…고객이 문의에서 규격을 밝혔습니다」 |

프롬프트(`agent-draft-prompt/v6`)에 규칙 하나가 붙는다:

> 확정되지 않았다고 적혀 있으면, 근거에 수치나 사양이 있더라도 그것을 이 고객의 상품에 대한 확정된
> 사실로 단정하지 마세요. 규격에 따라 달라질 수 있음을 밝히고 어떤 규격을 쓰실지 되물으세요.
> 근거의 수치는 일반적인 기준으로만 언급할 수 있습니다.

**판매자의 근거를 숨기지 않는다.** 등록된 FAQ를 못 쓰게 만드는 것은 다른 종류의 거짓말이고, 판매자가
쓴 것을 판매자 대신 검열하는 일이다. 바뀌는 것은 그 수치가 **닫는 문장**이 되느냐 **되묻는 문장**이
되느냐다.

**「적용 범위」 줄은 언제나 존재한다** — 주문 상태 줄과 같은 이유로. 없는 섹션은 모델에게 「여기서는
해당 없음」으로 읽히고, 있는 섹션은 「이것을 보라」로 읽힌다.

## 3. payload floor는 움직이지 않았다

이 줄은 **질문에 대한 사실**이지 판매자 카탈로그가 아니다. 옵션 이름을 되풀이하지 않는다 —
`VARIANT_NAMED`일 때조차 「고객이 규격을 밝혔습니다」라고만 말한다. `AgentDraftPayloadFloorTest`에
직렬화 바이트 위의 assertion이 하나 추가됐다.

## 4. 이 계약이 증명하는 것과, 증명할 수 없는 것

테스트는 **분류**와 **모델이 무엇을 들었는가**를 검증한다. 모델이 실제로 쓴 문장은 검증하지
않는다 — 그것은 이 저장소 안 어떤 것의 결정론적 함수도 아니고, 백엔드의 다른 모든 프롬프트가 같은
한계 아래 있다. 벤더의 샘플링을 red build로 만드는 것은 측정이 아니다.

| 케이스 | 검증 방식 |
|---|---|
| A · variant-independent FAQ | `NOT_VARIANT_SENSITIVE` — 추가 제약 없음 |
| B · variant-dependent + 규격 없음 | `VARIANT_UNRESOLVED` + 프롬프트에 단정 금지·되묻기 규칙 존재 |
| C · variant-dependent + 규격 명시 | `VARIANT_NAMED` — 옵션 조합의 **모든** 토큰이 문의에 나와야 한다 (한 단어 겹침은 우연) |
| D · 근거 0 | 「(없음)」이 명시되고 지어내지 말라는 규칙이 걸린다 |

## 5. 남은 한계 (고치지 않고 적는다)

1. **variant-specific evidence lane은 존재하지 않는다.** 상품 지식은 상품에 묶이므로, C가 참이어도
   「그 규격에 대한 근거」를 골라 줄 수는 없다. 만들려면 새 knowledge ontology가 필요하고 그것은 금지됐다.
2. **NAVER는 variant 행을 하나도 만들지 않는다.** 그래서 NAVER 문의에서 `VARIANT_NAMED`는 오늘
   도달 불가능하다 — 상품에 옵션 행이 없으면 대조할 대상이 없다.
3. **키워드 분류는 무디다.** false positive는 헤지 문장 하나를 더 만들고, false negative는 오늘의
   동작을 남긴다. 그 비대칭이 단어 목록을 넓게 잡은 이유이며, 이것으로 **무엇을 답할지**는 정하지 않는다.
4. **근본 원인은 지식 자체에도 있다.** 판매자의 FAQ가 규격을 구분하지 않는다는 사실은 이 패키지가
   고칠 수 없다. 판매자가 상품 지식을 고치는 것이 진짜 수리이고, 그때까지 초안은 되묻는다.

## 6. Evidence UX — 인용을 확인 가능하게

같은 사건이 화면 결함도 하나 드러냈다. 초안 아래에는 「AI가 확인한 내용 · 상품 정보 1개」만 있었고
기본 접힘이었으며, 열면 제목 **「자주 묻는 질문 - 접착과 재부착」**만 보였다. 전선 가닥 수에 대한
답변 옆에 접착에 대한 제목이 있었고, 판매자는 그 문서 안에 바로 그 Q&A가 들어 있다는 것을 알 방법이
없었다. **제목은 포인터이지 확인이 아니다.**

그래서:

- **첫 근거는 펼쳐진다** — 출처 종류 · 제목 · 발췌.
- **나머지는 접힌다** (`나머지 근거 N개 · 상품 정보 2개 · 과거 답변 1개`). 네 개를 다 펼치면 모든 초안
  아래에 인용문 네 덩이가 쌓이는 반대쪽 실패가 된다.
- **locator는 화면에 없다.** chunk 주소를 보고 행동하는 판매자는 없다.
- 발췌는 **드래프터가 실제로 본 문장**에서 온다. 생성 시점에는 손에 들고 있던 passage를,
  나중에 다시 열 때는 출처에서 읽어 온다(`DraftEvidenceSnippets`). 텍스트 사본은 여전히 하나뿐이다.
- 삭제된 지식 문서는 **발췌 없는 인용**이 된다. 인용은 초안이 무엇 위에 섰는지의 기록이므로 사라지지 않는다.

## 7. 시간 표기 — 한 화면, 한 숫자

같은 문의가 목록에서 「17분 전」, 상세에서 「방금」으로 보였다. `relativeTime`과 `waitedLabel`이 각자
버킷을 갖고 있었기 때문이다 — 앞의 것은 주(week) 칸이 없고, 뒤의 것은 분(minute) 칸이 없었다.

이제 사다리는 하나다(`lib/elapsed.ts`): 방금 / N분 / N시간 / N일(<7) / N주(<31) / N개월(<365) /
1년 넘음, 모든 칸에서 floor. **숫자와 단위는 한 곳에서 정하고, 말투만 각자 고른다** — 목록은 언제
왔는지를 말하고(「17분 전」) 작업 창은 얼마나 기다렸는지를 말한다(「17분째」). 한 사실에 대한 두 문장은
괜찮고, 두 숫자는 괜찮지 않다.

## 8. Product Grounding Groundwork (2026-08-26) — 착수, 라이브 증명 **PENDING**

§5가 「판매자 FAQ가 규격을 구분하지 않는다」를 한계로 적었지만, 감사해 보니 그보다 앞선 결함이
있었다. **판매자는 답을 적어 두었고, 우리가 그 페이지를 읽지 않고 있었다.**

- **원인은 이미지가 아니라 endpoint 선택이었다.** 카탈로그 sweep이 부르는
  `POST /v1/products/search`(LIST)는 `detailContent`·`optionCombinations`·`storeKeepingUrl`을
  **보내지 않는다**. `NaverProductsClient`는 그 셋을 매핑해 두고도 한 번도 받은 적이 없다
  (NAVER 발 description fact 0 · variant 0, 같은 코드가 다른 두 채널에서는 12와 405를 만든다).
  단건 리소스 `GET /external/v2/products/channel-products/{channelProductNo}`는 보낸다 —
  응답 스키마에서 `originProduct.detailContent`는 **필수**다. 계약은 사본으로 고정했다:
  `docs/vendor/naver-commerce-api/get-v2-products-channel-products-channelProductNo.md`.
- **키는 이미 우리가 들고 있다.** `channel_products.external_product_id`가 곧 `channelProductNo`이므로
  새 식별자 어휘도, id 발견 단계도 없다.
- **작성자 축은 문서 종류 축과 다르다.** `KnowledgeAuthorship`(V77의 `authored_origin`)은
  `KnowledgeSourceType`과 직교한다: 판매자가 우리 화면에 입력한 것 ·
  판매자가 자기 채널 상세페이지에 쓴 것 · **이미지에서 AI가 뽑아낸 것**. 셋째 값은 **선언만 되어
  있고 생산자가 없으며**, 없다는 사실 자체가 테스트로 고정돼 있다(`FactConfidence.INFERRED`와 같은 기법).
  판매자 화면에서 앞의 둘은 「상품 상세페이지」로 같게 보이지만 저장은 구분한다.
- **전체 카탈로그 sweep은 만들지 않는다.** `ProductDetailEnrichment`는 상품 하나만 받고,
  세 트리거(신규/변경 · 상품이 확정된 실무 문의 · 상세 지식 부재/노후)는 **동등**하며 어느 것도
  두 번째 상품을 읽을 이유가 되지 않는다. 상세 텍스트의 사본은 **하나**다(지식 라이브러리에만;
  `desc:summary` fact로 이중 저장하지 않는다). 옵션만 기존 `ProductKnowledgeWriter`로 간다.
- **그림을 읽을지는 측정한 뒤에 정한다.** `DetailContentShape`가 페이지를 다섯으로 분류하고,
  이미지 이해가 정당화되는 것은 **`IMAGE_REFERENCES_ONLY` 하나뿐**이다. `MIXED`는 텍스트 경로가
  있으므로 그것부터 쓴다.

**라이브 증명 `LIVE_VERIFIED` — verdict `IMAGE_ONLY_GAP`** (2026-08-26, `apr-nv-detail-13250364547-r2`,
마켓플레이스 요청 **1회** · WRITE 0 · 저장 0).

**측정.** `GET /external/v2/products/channel-products/13250364547` 한 번으로
`shape=IMAGE_REFERENCES_ONLY` · `text_chars=104` · detailContent **이미지 26** · listing 이미지 10 ·
**옵션 20, 그중 id 보유 20** · `needs_image_understanding=true` · `variant_named_reachable=true`.

**이 측정이 실제로 닫은 것과 닫지 못한 것은 다르다.**

- **닫혔다 — `TEXT_GROUNDABLE` 기각.** 상세 본문의 텍스트는 104자다. 20개 규격 각각의 수용 가닥수를
  담을 수 있는 분량이 아니다. 상세 **텍스트** 경로에는 이 질문의 답이 없다.
- **닫히지 않았다 — 옵션 *이름*의 내용.** 옵션은 20개가 있고 전부 id를 들고 있어 **구조적으로 읽을 수
  있다**. 그러나 프로브는 설계상 판매자가 쓴 글자를 하나도 밖으로 내보내지 않는다(`DetailContentShape`는
  enum 하나와 정수 셋이 되고 옵션은 개수와 존재 플래그가 된다) — 그래서 **이름이 규격 라벨인지 규격 +
  스펙인지는 관측되지 않았다**. 이것은 결함이 아니라 그 바닥의 값이다: 판매자를 보호하는 sanitization이
  같은 이유로 A(`STRUCTURED_GROUNDABLE`)와 C(`IMAGE_ONLY_GAP`)의 판별을 1회 예산 안에서 불가능하게 만든다.
  **가르는 비용은 정확히 READ 1회**이며, 그것은 새 승인을 요구한다. — **그 1회를 썼다: §8-1.**

**판정 `IMAGE_ONLY_GAP`**(provisional) — 근거 둘: 위 측정(상세 텍스트 경로 닫힘, 그림 26장), 그리고
**판매자 자신의 진술**(규격별 수용 가능한 전선 개수는 상품 상세페이지 **이미지**에 있다, product-owner
2026-08-26). 추론으로 메운 칸은 없고, 반증 가능한 형태로 적는다 — 옵션 이름이 그 수치를 들고 있다면 이
판정은 A로 바뀌며, 그것을 확인하는 방법은 위에 적힌 READ 1회다.

### 8-1. 그 READ 1회 — `VARIANT_LABEL_ONLY`, 그리고 `IMAGE_ONLY_GAP` CONFIRMED

**라이브 증명 `LIVE_VERIFIED`**(2026-08-26, `apr-nv-option-13250364547-r1`, 같은 endpoint,
마켓플레이스 요청 **1회** · WRITE 0 · 저장 0 — `product_variants` 405 그대로이고 대상 상품은 여전히 **0**).

관측 한 줄:

```
options=20 axes=2 spec_bearing=20 capacity_bearing=0
patterns=[화이트 / #호(##개), 그레이 / #호(##개), 블랙 / #호(##개)]
```

**판매자 콘텐츠는 자릿수를 지운 형태로만 나왔다.** `16x10mm` → `##x##mm`, `2~3가닥` → `#~#가닥`.
판정을 가르는 것은 **판매자가 쓴 단어**이고 카탈로그를 재현하는 것은 **그가 고른 값**이므로, 앞은 남기고
뒤는 버린다(`OptionSemantics`). 보고되는 패턴은 최대 **3개**이며 20개 전체 덤프는 하지 않는다.

- **닫혔다 — variant identity는 structured data에 있다.** 축은 **2개**(색상 · 규격), 20/20이 규격 단위
  토큰을 들고 있고 20/20이 id를 들고 있다. 즉 `SpecApplicability.VARIANT_NAMED`는 NAVER에서 처음으로
  **구조적으로 도달 가능**하다 — 오늘 저장된 variant 405가 전부 Coupang인 것은 수집 경로의 문제이지
  채널이 안 준 것이 아니다.
- **닫혔다 — 수용 가닥수는 거기에 없다.** 20개 라벨 **전수**에서 관계어(`가닥`·`심선`·`코어`·`수용`)가
  **0건**. 규격은 이름을 가졌지만 그 규격이 전선을 몇 가닥 받는지는 옵션 데이터가 말하지 않는다.

**`(##개)`를 가닥수로 읽지 않았다.** 그것이 정확히 이 사건을 만든 추론이다 — `16x10mm`에 숫자가 둘 있다고
「16가닥」이 되지 않듯, 괄호 안의 수량이 수용량이 되지도 않는다. `OptionSemantics`는 관계를 말하는
**단어**를 요구하고 숫자만으로는 아무것도 승격시키지 않는다. 표시자 목록은 닫혀 있고 **의도적으로 과소
계수**하며, 사람이 무엇을 거절했는지 볼 수 있도록 마스킹된 패턴을 옆에 함께 적는다.

**결론.** 후보 B `VARIANT_LABEL_ONLY` ⇒ **`IMAGE_ONLY_GAP` CONFIRMED**. 그리고 이것은 나쁜 결말만은
아니다 — 그림에서 사실을 꺼내는 날이 온다면 그 사실을 **정확한 variant에 붙일 기반이 이미 채널에 있다**
(§6의 「규격 라벨 없는 수치는 저장 거절」이 실행 가능하다는 뜻이다). 다음은 구현이 아니라
**product-owner decision**이다: `docs/image_product_knowledge_v1.md`.

**그래서 이 org의 오늘 상태.** 상품 `8722bf9c`에는 variant **0**, product_fact **3**(전부 taxonomy —
manufacturer · category · brand), 판매자 작성 문서 **3**(USAGE · FAQ · POLICY). 「전선이 몇 가닥까지
들어가나요?」의 답이 될 **현재 사실 근거는 이 저장소 안에 존재하지 않으며**, 초안이 인용했던 문장은
규격을 구분하지 않는 상품 단위 FAQ였다(§1). 즉 이 사건의 최종 원인은 검색도 모델도 아니라
**근거가 그림 안에 있었다**는 것이다.

**다음 단계는 OCR 구현이 아니라 설계다** — `docs/image_product_knowledge_v1.md`(설계만, 구현 0).

**경위.** 같은 승인의 1차 시도 `apr-nv-detail-13250364547`는 게이트웨이가 이 머신의 호출 IP를 거부해
(`GW.IP_NOT_ALLOWED`, 토큰 발급 단계, **마켓플레이스 요청 0회**) 실행되지 못했다. 이번 실행 전 preflight도
한 번 **빨간불로 멈췄다**: 실제 egress와 이 배포가 선언한 NAVER advertised egress가 **서로 다른 네트워크**였고,
그 상태에서는 요청 0회로 STOP했다. product-owner가 등록 상태를 확인한 뒤 **실행 환경의 선언만** 실제와 맞게
정정했다(새 IP 등록 없음, 실제 IP는 repo·docs에 커밋하지 않는 원칙 유지).

## 9. 답변 근거 상태 — `GROUNDED` / `NEEDS_CLARIFICATION` / `NO_ANSWER_BASIS` (2026-08-26)

§8이 「닫지 않았다」고 적어 둔 것 중 하나가 여기서 닫혔다. **새 classifier는 없다** — 세 상태는
이미 있던 두 enum의 **순수 함수**다(`AnswerBasisState.of(DraftKnowledgeState, Applicability)`,
입력 2개, 텍스트 미열람, 모델 호출 0, 단어 목록 0):

| 라이브러리 판정 | 규격 적용 범위 | 답변 근거 상태 |
|---|---|---|
| `GROUNDED` 아님 | 무엇이든 | **`NO_ANSWER_BASIS`** |
| `GROUNDED` | `VARIANT_UNRESOLVED` | **`NEEDS_CLARIFICATION`** |
| `GROUNDED` | `NOT_VARIANT_SENSITIVE` · `VARIANT_NAMED` | **`GROUNDED`** |

부재가 모든 것을 이긴다. 근거가 없는데 되묻는 초안은 여전히 근거 없는 답변이고, 과거 답변만으로는
애초에 `DraftKnowledgeState.GROUNDED`에 닿지 못하므로 여기서 다시 판단하지 않는다.

**`NO_ANSWER_BASIS`에서는 모델을 호출하지 않고 초안도 저장하지 않는다**(product-owner 결정).
화면은 **「답변 기준이 필요합니다.」**와 무엇이 빠졌는지 한 줄을 보이고, 편집기는 열려 있으며,
판매자가 직접 쓴다. 승인이 묶일 버전이 만들어지지 않는다.

**그 결과 결정론적 fallback drafter가 사라졌다.** 그것이 쓰던 문장은
「문의하신 내용을 확인한 뒤 정확한 안내를 드리겠습니다」였다 — 근거 0으로, 판매자의 목소리로, 아무도
승인하지 않은 약속. Organization Answer Style v1이 판매자가 승인한 문장을 줄 때까지 임의의 promise
template은 만들지 않는다(그 금지는 `AnswerBasisStateTest`가 문자열로 고정한다). 따라서 **모델이 쓰지
않으면 초안도 없다** — capability off · 일일 예산 소진 · 벤더 거절 모두 같은 결말이고, 이유는
`unavailableMessage`로 따로 말한다. `DraftAuthorKind.RULE`은 기존 행을 위해 남지만 **더 이상
생산되지 않는다**.

### 9-1. 근거 상태와 운영 상태는 다른 질문이다 (2026-08-27)

위 문단에는 결함이 있었고 실제로 구현돼 있었다: 「모델이 쓰지 않으면 초안도 없다」를 지키면서
**보고까지 `NO_ANSWER_BASIS`로** 했다. 그래서 근거가 완벽한 질문에서 벤더가 응답하지 않았을 때
화면은 「답변 기준이 필요합니다」라고 말했다 — 판매자는 이미 등록해 둔 상품 지식을 **한 번 더**
등록하러 갔을 것이다.

`AnswerBasisState`는 **증거**에 대한 진술이다. 다음은 **기계**에 대한 진술이고 다른 칸으로 간다:

| 상황 | 문장 |
|---|---|
| 근거 있음 + 벤더 무응답 | 「답변 초안을 생성하지 못했습니다. 잠시 후 다시 시도해 주세요.」 |
| 근거 있음 + 예산 소진 | 「오늘 사용할 수 있는 AI 처리량을 모두 썼습니다…」 |
| capability OFF | 「AI 답변 초안 기능이 켜져 있지 않습니다.」 |
| 상세페이지 READ 실패 | 「상품 상세 정보를 확인하지 못했습니다.」 |
| 검색이 **끝났고** 쓸 근거 0 | 「답변 기준이 필요합니다.」 — **여기서만** |

**새 enum은 만들지 않았다.** 기존 `ProductDetailEnrichmentTrigger.Outcome`(이미 `READ_FAILED`를
갖고 있었다)과 `GeneratedDraftView`의 메시지 칸으로 충분했고, 그 칸의 이름만
`quotaMessage` → **`unavailableMessage`**로 정직해졌다. `AnswerBasisState`는 입력 2개짜리 순수
함수 그대로이며 값도 셋 그대로다.

화면 규칙은 **우선순위 하나**다: `unavailableMessage`가 있으면 그것이 카드가 되고
「답변 기준이 필요합니다」는 렌더되지 않는다. 특히 상세페이지 READ 실패에서 그렇다 —
**끝까지 보지 못한 것과, 보고 나서 없는 것은 다른 주장이다.**

「상품 상세 정보를 확인 중입니다.」(PENDING)는 **오늘 생산자가 없다**. enrichment는 동기이고 이미지
lane은 존재하지 않으므로 draft 시점에 in-flight일 수 없다 — enforcement 0인 상태 값을 미리 두지
않는다는 같은 규율로 만들지 않았고, 이미지 lane이 비동기로 붙는 날 그 receipt가 생산자가 된다
(`docs/image_product_knowledge_v1.md` §10-2 · §10-4).

`NEEDS_CLARIFICATION`은 반대로 **진짜 답변**이다. 근거는 있고 고객만 아는 사실 하나가 비었을 뿐이므로,
그 하나를 묻는 것이 답변 전체다 — 없는 정책도 없는 수치도 덧붙이지 않는다.

**Proactive에도 같은 규율이 적용된다:** 초안이 없으면 `ProactivePreparedAction.DRAFT_PREPARED`가 아니라
`NONE`이다. 준비되지 않은 것을 「준비됨」으로 세는 카드는 이 lane이 피하려던 바로 그 과장이다.
