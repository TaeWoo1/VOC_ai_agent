# Knowledge Gap Resolution v1 — 모르는 것을 판매자에게 묻고, 다시 판단한다

> **상태: 구현됨 · 로컬 스키마 반영됨 · 마켓플레이스 호출 0 · 모델 호출 0.**
> `NO_ANSWER_BASIS`가 **정확하게** 동작해도 판매자가 그 자리에서 지식을 보충할 수 없으면 같은 질문은
> 영원히 같은 답을 받는다. 이 패키지는 그 순환을 닫는다: **모른다 → 무엇이 필요한지 말한다 →
> 판매자가 한 문장 쓴다 → 같은 문의를 다시 판단한다.** 전송은 이 흐름 안에 **없다**.
>
> 범위는 **Product / Variant 지식까지**다. 배송 일정·재고·사은품·프로모션·교환/반품·채널 규칙·
> ontology·generic operational fact editor·knowledge graph는 **구현하지 않았다**. 장기 방향은
> `docs/operational_knowledge_direction_v1.md`가 그대로 소유한다.

## 1. 먼저 감사 — 이미 있던 것과 없던 것

새로 만들기 전에 기존 seam을 셌다. **대부분 이미 있었다.**

| 필요한 것 | 상태 | 어디에 |
|---|---|---|
| Product Knowledge CRUD | **있음** | `ProductKnowledgeLibraryService` + `/api/products/{id}/knowledge/sources` |
| 저장 즉시 색인 | **있음** | `ProductKnowledgeIndexer` — 같은 트랜잭션, 큐 없음 |
| 판매자 입력 provenance | **있음** | `KnowledgeAuthorship.SELLER_ENTERED_KNOWLEDGE`(기본값) |
| 문의 ↔ 상품 결합 | **있음** | `InquiryProductBinding.SOURCE_EXACT` / `USER_CONFIRMED` |
| 초안 재생성 | **있음** | `POST /api/inquiries/{workItemId}/draft/generate` (append-only 버전) |
| 판매자용 지식 편집 화면 | **있음** | `ProductKnowledgeLibrary.tsx` (상품 상세 화면) |
| **문의 화면에서 지식으로 가는 길** | **없었음** | — |
| **지식의 규격(variant) 적용 범위** | **없었음** | — |
| **무엇이 부족한지 구체적으로 말하는 문장** | **없었음** | 일반 문장만 |

그래서 이 패키지가 새로 만든 것은 그 셋뿐이고, 나머지는 전부 재사용이다.

## 2. `NO_ANSWER_BASIS` → 지식 추가 흐름

문의 상세의 「답변 기준이 필요합니다」 카드 안에 **「답변 기준 추가」**가 붙는다. 누르면 그 자리에서
작은 폼이 열린다 — **답변 기준 내용**과 **적용 범위**, 두 가지뿐이다.

- 상품을 **다시 검색하게 하지 않는다**: 상품·채널·문의 맥락은 이미 화면이 들고 있고,
  `GeneratedDraftView.productId`가 저장 대상이다.
- **상품이 없으면 이 버튼은 나오지 않는다.** 저장할 곳이 없는 입력칸은 없는 것만 못하고, 그 경우
  카드가 이미 「어떤 상품에 대한 것인지 연결하면」이라고 말하고 있다.
- 큰 지식 관리 화면으로 보내는 것은 **주 흐름이 아니다**. 상품 라이브러리는 그대로 있고, 여기서 쓴
  문서도 거기서 수정·삭제된다.
- 제목은 **첫 줄**에서 만든다(60자 상한). 폼을 한 칸으로 두기 위한 노트 관습이고, 라이브러리에서
  언제든 고칠 수 있다.
- 라벨은 「내용」이 아니라 **「답변 기준 내용」**이다 — 같은 화면 아래에 답변 본문의 「내용」이 이미 있고,
  같은 이름표 두 개는 판매자가 고객에게 보낼 답을 라이브러리에 쓰게 만드는 방법이다.

**저장은 저장이다.** 저장 → 재색인 → 근거 검색 → 적용 가능성 → 초안 재생성까지만 하고 멈춘다.
승인 경계·Action Executor·전송은 전부 제자리이며, 구조 테스트가 그 셋을 이름으로 막는다.

## 3. Provenance

판매자가 직접 쓴 것은 **`SELLER_ENTERED_KNOWLEDGE`**로 저장된다 — 기본값이므로 코드 변경 0.
AI가 쓴 것으로 바꾸지 않고, AI가 쓴 것을 판매자가 쓴 것으로 바꾸지도 않는다.

저장은 기존 `ProductKnowledgeIndexer`를 지나므로 **즉시 검색 가능**하다. 문서는 생겼는데 청크가 없던
2026-08-27 이전의 `TEXT_INDEXED` 결함은 그 클래스를 뽑아내면서 닫혔고, 여기서도 같은 클래스를 쓴다 —
`chunks`가 0이면 화면이 「AI가 인용할 수 없습니다」라고 말한다.

## 4. 규격(variant) 적용 범위 — 기존 seam으로는 표현할 수 없었다

§5가 요구한 네 가지를 먼저 적는다.

**(a) 어떤 relation이 필요한가.** 「이 문장은 이 상품의 **이 규격**에 대한 것이다」. 즉
knowledge document → product_variant 의 **0..1** 관계다.

**(b) 왜 기존 schema로 불가능한가.** `product_knowledge_sources`의 축은 둘뿐이다 —
`source_type`(무엇에 대한 글인가)과 `authored_origin`(어떻게 생긴 글인가). 어느 쪽도 「누구의 규격에
대한 주장인가」를 담지 못한다. `channel_source_ref`는 채널 유래 문서의 **동일성** 키라 재사용하면
재수집이 판매자의 글을 덮어쓴다. 남는 선택지는 본문에 `[2호] 3~4가닥`처럼 **적어 두고 나중에 regex로
복원**하는 것인데, 그것은 migration도 constraint도 없는 스키마다 — 금지된 쪽이다.

**(c) 최소 migration.** `V79__knowledge_variant_scope.sql` — **한 칸**이다.

```sql
alter table product_knowledge_sources
    add column variant_id uuid references product_variants (id);
create index idx_pk_sources_variant on product_knowledge_sources (org_id, product_id, variant_id);
```

**(d) product-level과 variant-level의 공존.** `null`은 「모른다」가 아니라 **「전체 상품 공통」**이다 —
기존 모든 행이 이미 그것이므로 backfill은 **없음**이 정답이다. 두 scope뿐이고 세 번째는 표현 불가능하다.
그리고 FK가 **울타리**다: 규격은 채널이 말한 행을 가리키므로 판매자가 임의의 규격 이름을 만들 수 없다
(다른 상품의 규격을 붙이려 하면 400이며, 조용한 null이 아니다 — 조용한 null은 한 규격에 대한 주장을
전 규격에 대한 주장으로 **넓히는** 것이다).

### 4-1. 검색이 무엇을 허용하는가 — 비대칭이 핵심이다

`KnowledgeVariantScope`는 두 상태뿐이고, 둘의 규칙이 **다르다**.

| 상태 | 전체 상품 공통 문서 | 다른 규격 문서 | 그 규격 문서 |
|---|---|---|---|
| `of(3호)` — 고객이 규격을 밝혔다 | 사용 | **제외** | 사용 |
| `unresolved()` — 아무도 말하지 않았다 | 사용 | **사용** | 사용 |

- 고객이 3호라고 말했을 때 2호 문서는 **약한 근거가 아니라 다른 사람의 물건에 대한 근거**다. 그래서
  랭킹 이후가 아니라 **문서 집합 단계에서** 빠진다 — 나중에 거르면 그 문서가 4칸 중 하나를 차지했다가
  사라져서, 멀쩡한 전체 공통 답이 있는 질문이 빈손으로 돌아온다.
- 아무도 규격을 말하지 않았을 때는 **아무것도 빼지 않는다.** 규격별 문서야말로 「이 질문은 답할 수 있다」의
  증거이고, 그것을 숨기면 화면은 라이브러리가 비었다고 거짓말한다. 정직한 답은 **되묻는 것**이다.

즉 이 클래스는 신중해 보이려고 근거를 숨기지 않는다. **다른 물건에 대한 것임이 증명된 근거만** 숨기고,
증명할 수 없으면 아무것도 숨기지 않은 채 고객에게 묻는다.

규격 확정은 **검색보다 먼저** 일어난다(`InquiryDraftComposer`). 이것이 이 패키지의 순서 변경이다.

## 5. 다시 판단 — 지식 하나가 늘었다고 무조건 GROUNDED가 아니다

저장 후 같은 문의에 대해 `DraftKnowledgeState` + `SpecApplicability`를 **다시** 계산한다. 결과는 셋이다.

| 판매자가 추가한 것 | 문의가 규격을 말했나 | 결과 |
|---|---|---|
| 상품 공통 사실, 질문에 해당 | (질문이 규격 민감하지 않음) | **`GROUNDED`** — 근거 있는 초안 |
| 규격별 사실 | 아니오 | **`NEEDS_CLARIFICATION`** — 규격을 되묻는 초안 |
| 규격별 사실 | 예, 우리가 아는 규격 | **`GROUNDED`** — 그 규격 근거만 |
| 질문에 해당하지 않는 사실 | — | **`NO_ANSWER_BASIS` 유지** |
| 다른 규격의 사실뿐 | 예, 다른 규격 | **`NO_ANSWER_BASIS`** — 그 문서는 드래프터에 도달조차 하지 않는다 |

세 번째 줄에 함정이 하나 더 있다. 이 상품처럼 **규격이 등록돼 있지 않은** 리스팅에서 규격 민감한
질문은 지식을 추가해도 `VARIANT_UNRESOLVED`이므로 `NEEDS_CLARIFICATION`이다 — 근거는 생겼고, 남은 한
가지 사실은 **고객이 가진 것**이다. 이것은 결함이 아니라 이 패키지가 지키려는 규칙 그 자체다.

드래프터가 듣는 줄도 한 겹 늘었다: 근거 중 **하나라도** 특정 규격 전용이고 규격이 확정되지 않았으면
「그 수치를 이 고객의 규격에 대한 사실로 쓰지 말고 되물으세요」가 붙는다. payload floor는 그대로 —
그 줄은 **옵션 이름을 싣지 않는다**.

## 6. 무엇이 부족한지 말하기 (§9)

「답변 기준이 필요합니다」 아래 한 줄이 **고객이 쓴 명사를 그대로 인용**한다.

> 등록된 상품 지식·운영 정책에 **「가닥」** 관련 내용이 없습니다. 규격에 따라 답이 달라진다면 규격별로
> 등록할 수 있습니다.

- **새 classifier가 아니다.** `SpecApplicability`가 이미 스캔하던 단어 목록을 둘로 **쪼갠 것**이 전부이고
  (단어는 하나도 더하거나 빼지 않았다), 합집합은 여전히 판정을 결정한다. 나눈 이유는 하나 —
  판매자에게 무엇을 쓰라고 말하려면 **명사**가 필요하고 「'맞나요' 관련 내용이 없습니다」는 문장이 아니다.
- **LLM이 만들지 않는다.** 두 번째 문장(규격)도 이미 계산된 verdict에서만 붙는다.
- 질문이 아무 속성도 지목하지 않으면 **일반 문장**으로 돌아간다. 모호한 질문에 모호한 답은 옳은 결과다.

## 7. 판매자가 직접 쓴 답변은 지식이 되지 않는다 (§10)

`NO_ANSWER_BASIS`에서도 답변 상자는 열려 있고 판매자가 직접 쓴다. 그 문장은 **자동으로 Product
Knowledge가 되지 않는다.**

실제 답변은 이 고객의 주문·말투·예외가 섞인 것이고, 객관적 상품 지식은 다음 고객에게도 참인 것이다.
승격하면 이 고객의 예외가 다음 고객에게 규칙으로 나간다. 나중에 명시적인 「이 답변을 답변 기준으로
저장」이 생길 수 있고 **그것은 별도 결정**이다 — 판매자가 말할 수 있게 되기 전까지 아무것도 대신
결정하지 않는다.

구조로 고정했다(`KnowledgeWriteFenceTest`): 지식 문서를 **만들 수 있는 클래스는 셋뿐**이고
(라이브러리 편집기 · 상세페이지 텍스트 lane · 이미지 lane), `inquiry/reply` · `inquiry/publish` ·
`inquiry/proposal` · `inquiry/lifecycle` 어디에도 지식 writer가 **없다**.

## 10. 실행된 것과 실행되지 않은 것

**실행됨(로컬, 승인 불필요 — 채널 무접촉):** 커넥터·스케줄러를 끈 채 백엔드를 기동해 **V79를 실제 로컬
DB에 적용**했다. 마이그레이션 1건 적용, 기동 성공, 로그에 채널·모델·상세 읽기 활동 **0**, ERROR/WARN **0**.
읽기 전용 확인: 기존 지식 문서 **5건 전부 `variant_id` null**(= 전체 상품 공통) · 청크 없는 문서 **0** ·
규격 후보 **425**개 · FK `product_knowledge_sources_variant_id_fkey` 존재.

**실행되지 않음:** 브라우저로 판매자 화면을 직접 몰지 않았다 — 로그인은 운영자의 일이고, 실제 상품에
가짜 「몇 가닥」 숫자를 넣지 않는다는 §14의 금지가 UI 왕복 증명과 정면으로 만난다. 화면 동작은
렌더 테스트 4건으로 고정했다(CTA 노출 · 상품 없으면 미노출 · 규격 선택 저장 · 기본 null 저장).

**마켓플레이스 호출 0 · 모델 호출 0 · 실제 판매자 지식 삽입 0.**
