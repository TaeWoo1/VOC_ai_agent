# Inquiry v3 WP-1 — Eval Asset Recovery + Deterministic Authority Layer

2026-09-20 · branch `feat/review-decision-workspace-v1` · design: `docs/inquiry_architecture_v3.md` (adopted by the product owner
on 2026-09-20, with the eight decisions in §2).

**What this package is — and is not.** It adds the deterministic authority layer every later planner and resolver depends on:
- the capability registry
- the entity / scope / provenance contract
- the ENTITY_STATE resolver foundation
- the plan gold contract
- the v2 authority-confusion fence

It is not a new AI. It adds **no Resolution Planner, no PROCEDURE executor and no replacement for the CoverageJudge**.

**Zero-counts:**
- model calls 0
- marketplace calls 0
- external writes 0
- migrations 0
- changes to the dev DB `sellerops`: none

The eval runs used throwaway copies of the S0/S1 clones; every copy was dropped afterwards. The new flag is
`sellerops.inquiry-authority.fence.enabled` (env `SELLEROPS_INQUIRY_AUTHORITY_FENCE_ENABLED`), **default OFF**. It is deliberately
not under the `inquiry-decision` prefix: the fence is not part of the LLM capability, and `AgentDraftBoundaryTest` (no file
reads two capabilities' flags) caught the first placement.

## 3. Registry contract (`inquiry/authority/CapabilityRegistry`)

`snapshot(org, inquiry, productId, detail, lookup)` → `CapabilitySnapshot` (`capability-registry/v1`). It reads three stored
things: the channel code, whether a listing row exists, and the option count. It calls nothing. `derive(Inputs)` is pure, so the
whole policy is one function:

| capability | status rule | source of the rule |
|---|---|---|
| `KNOWLEDGE.PRODUCT` / `.CATALOGUE` | AVAILABLE iff a listing was resolved | — |
| `KNOWLEDGE.ORG` | AVAILABLE | — |
| `ENTITY.ORDER` fields | PAYMENT: exact read ∨ NAVER store. CANCELLATION / FULFILLMENT: exact read only. TRACKING: never | `ExactOrderLookupCapability` (Cafe24 only, and only when the caller allows `EXACT_ALLOWED`) · `NormalizedOrderStatus` (NAVER PAYED only) · `InquiryOrderFactReader.storedFact` (cancel/fulfil UNPROVEN from the store) · no tracking reader exists |
| `ENTITY.LISTING` fields | SALE_STATUS iff a `channel_products` row. OPTION_SALE_STATUS iff `product_variants` rows | `SellingStatus` (fail-closed UNKNOWN) |
| `PROCEDURE.ORDER_ACTION` | DECLARED_NO_EXECUTOR, always | decision 2 |
| `SELLER` | AVAILABLE | — |

The snapshot also carries four facts:
- **surface** — `InquirySurface`, from the channel's own `source_subtype`. Only NAVER 고객 문의 is ORDER_ATTACHED; anything
  unknown is PUBLIC.
- **binding** — `SOURCE_EXACT` only.
- **detail capability**
- **variant count** — the structured fact v2.2 §7 named as the missing input for `ae51c7f8`.

A planner may **name** an unavailable capability (a plan records what is needed). Code turns unavailability into a gap and
never into a different authority. `fingerprint()` is stable and moves with any fact, so it joins the calibration fingerprints.

## 4. Authority / source provenance model

- `Resolution(capability, state, gap, missing, ask, observed, preconditions)` — the unit every later layer reads. Its constructor
  holds these rules:
  - a gap reason is given ⇔ the state is CAPABILITY_GAP;
  - nothing asks for identity;
  - **a PROCEDURE never closes**;
  - an ENTITY_STATE step closes only on **FRESH** observations;
  - CONDITIONAL / NEEDS_CUSTOMER_INPUT must name what to ask.
- `ObservedField(field, value, AuthorityProvenance)`.
- `AuthorityProvenance(capability, entity: EvidenceScope, source, asOf, freshness)`.
  - Sources: `ORDER_STORED`, `ORDER_EXACT_READ`, `LISTING_STORED`, `OPTION_STORED`, `SELLER_KNOWLEDGE`, `ORG_KNOWLEDGE`,
    `CATALOGUE_FACT`.
  - The entity reuses v2.2's `EvidenceScope`, so an observation is always about *this* order or *this* listing and can be
    compared with evidence scope by the same key.
- `ResolutionState`: RESOLVED · RESOLVED_CONDITIONAL · NEEDS_CUSTOMER_INPUT · NEEDS_SELLER · CAPABILITY_GAP · FAILED.
- `GapReason`, split three ways:
  - **definite** — the system provably cannot act here:
    - `NOT_SUPPORTED` — a field or capability is not provided
    - `NOT_EXECUTABLE` — a procedure without an executor
    - `UNBOUND` — the channel named no instance
    - `STALE`
    - `UNPROVEN`
    - `UNAVAILABLE`
  - **possible** — a source exists that was not read (`ACQUIRABLE`) or cannot be read (`UNREADABLE_SOURCE`). The answer may or
    may not be in it.
  - **`DISABLED`**.

**Why possible gaps are named apart** — the diagnostic in §10 forced it. On real listings the detail page is pictures, and the
deterministic layer **cannot know** whether a need the seller never wrote about is answered in those pictures:
- Calling it `NEEDS_SELLER` would claim a seller shortfall it cannot prove.
- Calling it `NOT_SUPPORTED` would hide a seller shortfall behind a system limit.

It says exactly what it knows instead.

## 5. ENTITY_STATE resolver foundation (`EntityStateResolver`)

The resolver is pure. It reads the order fact the caller already has (`InquiryOrderFactReader` with the caller's
`OrderFactLookup`) and the stored listing state (`CapabilityRegistry.listingState`). It never reads again.

| order | → |
|---|---|
| not bound / no reference / no key | `CAPABILITY_GAP UNBOUND`. The binding decides even if a fact is handed in (E12) |
| ORDER_NOT_FOUND / SOURCE_UNAVAILABLE | `UNAVAILABLE` |
| a requested field the registry cannot observe here | `NOT_SUPPORTED`, with those fields |
| observed, not provably current | `STALE`. The fields are still recorded, with UNPROVEN freshness |
| observable, and this read did not prove it | `UNPROVEN` |
| all requested fields proven and fresh | `RESOLVED`, each field with provenance |

For a **listing**:
- An option status for an unnamed option on a multi-option listing → `NEEDS_CUSTOMER_INPUT(OPTION)`. It asks and never assumes.
- A named option not among the seller's labels → `UNAVAILABLE`. There is **no fuzzy match**.
- Older than `LISTING_STATE_MAX_AGE` = 24h → `STALE`. That is one catalogue-refresh cycle, the existing
  `sellerops.knowledge.bootstrap` cadence. The bound is a product parameter and is listed in §13.

## 6. v2 authority-confusion fence (`AuthorityFence`, default OFF)

It is applied in `InquiryDecisionEngine.decide` after `NeedAggregation.enforce` and before the basis, only when the assessor
hands it a context. The assessor does that only when the flag is on, v2 is on for the org, and the beans exist.

- **Inputs.** The snapshot and the order fact the spine lanes **already read** (`found.lanes().order()`). There are no new reads
  and no model call.
- **Rule.** A need closes only by its own authority, via the **v2 bridge** `NeedType → capability` (pinned in `vocabulary.json`
  `v2_bridge`):
  - **ORDER_STATE → ENTITY.ORDER.** Only THIS order's fresh fact closes it. v2.2 caught a policy-only **FULL**; the fence also
    catches the policy **CONDITIONAL** (A-arm T13a) and a stale or unbound fact (`AUTHORITY_UNRESOLVED`).
  - **ORDER_ACTION → PROCEDURE.** Never closed. Recorded as `NOT_EXECUTABLE`, with the order entity as a precondition.
  - **SELLER_DECISION → SELLER.** Never closed by evidence.
  - **Listing / policy → KNOWLEDGE.** An order fact alone does not close it. Unreadable detail → `UNREADABLE_SOURCE`; never read
    → `ACQUIRABLE`; otherwise `NEEDS_SELLER`.
- **Guarantees.**
  - It **never widens**: `withAuthority` throws if a status would become more covered.
  - It **never substitutes** an authority.
  - With the flag off, the engine returns exactly v2.2's results (`offIsV22`).
- **New `NeedResult` fields.** One component, `resolution` (null when off). Two enforcement values: `WRONG_AUTHORITY` and
  `AUTHORITY_UNRESOLVED`.
- **Known bridge limits.** These are for the WP-2 planner, not for more bridge rules:
  - A v2 need names no **field**. So an unresolved order need is tested against every order field, and TRACKING (never
    observable) makes it a `NOT_SUPPORTED` gap.
  - Four order remedies that v2 typed SELLER_DECISION are recorded as `NEEDS_SELLER`; the gold records them as procedures (§10).
    Neither ever closes, so this is safe.
  - One listing-*state* need is bridged to KNOWLEDGE.

## 7. Plan gold contract

- **Vocabulary.** `contracts/inquiry-authority/v1/vocabulary.json` is one file for everything: authorities, capabilities with
  wire ids, fields, states, gap reasons (and which are possible), customer inputs with kinds and askability, surfaces, step roles,
  and the v2 bridge. `AuthorityVocabularyContractTest` pins every Java enum and `AuthorityFence.planned` to it.
- **Row schema.** `contracts/inquiry-resolution-plan/v3/schema.json`:
  - `steps[{capability, role: CLOSES|PRECONDITION|CONTEXT, fields?, depends_on?}]`
  - `customer_inputs`
  - `expected_terminal`
  - `status: FROZEN|PENDING_ADJUDICATION` (+ `pending_reason`, `alternatives`)
  - A fallback to the seller is **not a step**.
- **Scorer.** `tools/inquiry-need-eval/plan.mjs`:
  - `validatePlans` — identity never asked; no bridge placeholder in a plan; a procedure is never expected to resolve; fields
    belong to their capability; every row has a closer.
  - `scoreBridge`.
  - `scorePlans` — the A-layer of Eval v2: required-authority recall, **ORDER miss = hard fail**, unnecessary authority, slot
    exactness.
  - `compareResolutions` — a possible gap is never counted as agreement or disagreement.
- **Gold v3.** Stored at `eval-store:inquiry-resolution-plan/v3` (manifest `contracts/inquiry-resolution-plan/v3/dataset.meta.json`).
  - 72 canonical needs: **66 FROZEN**, **6 PENDING**.
  - Terminal distribution of the frozen rows: NEEDS_SELLER 30 · UNREADABLE_SOURCE 14 · NOT_EXECUTABLE 7 · RESOLVED 7 ·
    RESOLVED_CONDITIONAL 5 · UNBOUND 2 · NOT_SUPPORTED 1.
- **v1 and v2 were withdrawn before use** — built, stored, then found wrong by this package's own diagnostic. Their manifests say
  why, and the store keeps them for the record.
  - **v1** mixed «next step» with «terminal» for never-read listings.
  - **v2** filed «answer is in the detail pictures» under the same word as «the channel does not provide this field».

**Rule proposed for all four.** Plan SELLER **only** when no statement the seller could teach once would answer the need next

for it can never be found, and **Repeat Seller Ask after Teach — a headline metric — can never fall** for that class. Under this
rule, `ae41a418` n2 and T7a/T7b (restock timing) stay SELLER. That is why they are frozen.

## 10. Diagnostic on the v1 assets (offline oracle, no model)

`InquiryNeedEvalIT EVAL_DECISION=oracle` means: gold needs as the plan, gold evidence over the production collector as the judge.
It ran on throwaway S0/S1 copies with the fence off and on. The observation gained resolution fields only when the fence runs, so
an OFF observation is unchanged.

| | S0 | S1 (NAVER detail read) |
|---|---|---|
| observation rows that differ, fence on vs off, beyond the new fields | **0 / 67** | **0 / 67** |
| need statuses the fence changed (gold verdicts never cite the wrong authority) | **0 / 72** | **0 / 72** |
| resolution = gold terminal (66 frozen) | 26 | **40** |
| possible gap where the gold terminal is NEEDS_SELLER | 36 (ACQUIRABLE — read the detail first) | 22 (UNREADABLE_SOURCE — picture pages) |
| differs | 4 | 4 |

- **The 4 are identical on both snapshots:** `0c582144` · `9b8cc5a5` · `515dd536` · T10b. Each is an order remedy v2 typed
  SELLER_DECISION; the bridge says NEEDS_SELLER and the gold says `NOT_EXECUTABLE`. Neither closes, so this is safe, and it is the
  bridge's documented limit.
- **Bridge authority agreement** with the frozen gold: **61/66 (92.4%)** — those 4 plus `ae41a418` n1 (listing state bridged to
  knowledge).

**What this shows.** Where the system knows, the deterministic layer tells the capability's limit apart from the seller's
knowledge: procedure not executable, order unbound, field unsupported. On this seller's catalogue (every NAVER detail is
pictures), **22 needs cannot be separated by any deterministic rule.** Only an image reader or a seller's «not in the page»
separates them. Before the vocabulary named it, that limit sat inside NOT_SUPPORTED.

## 14. Next — WP-2, and when a model is first needed

**WP-2 — Resolution Planner, contract to shadow.**
1. **Build (no model).** The planner prompt and a strict schema generated **from the registry snapshot** (capability, field and
