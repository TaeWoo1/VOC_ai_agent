# Operations Home v1 — 로그인하면 「지금 확인할 것」이 화면에 있다

**날짜:** 2026-09-13 · **상태:** `IMPLEMENTED · LOCAL_BROWSER_QA_PASS`
**마이그레이션 0 · 새 테이블 0 · 새 enum 0 · 모델 호출 0 · 마켓플레이스 0 · WRITE 0 · DB 행 변경 0**

판매자가 로그인했을 때 지금 확인할 것을 한 화면에서 이해하고 바로 작업으로 들어갈 수 있게 한다.
**chat-first는 유지하되 chat-only가 아니다** — 네 영역이 대화 위에 서고, 대화는 그대로 아래에 있다.

---

## 0. 감사 — 하나만 없었다

브리프는 「org-level roll-up read 하나를 우선 고려」라고 했다. 감사 결과 정확히 그랬다.

| 영역 | 이미 org-wide였나 |
|---|---|
| 반복 문제 | **있음** — `GET /api/review-issues`, `IssueOrdering.ACTIVE_FIRST` 순서 그대로 |
| 최근 수집 상태 | **있음** — `ChannelCoverageService.coverage(org, VISIBLE_CODES)`, `ChannelCoverageRow` |
| 준비된 작업(문의) | **있음** — `InquiryWorkItemPhase.AWAITING_SELLER` + `InquiryReplyDraft` 존재 |
| 지금 확인할 리뷰 | **없음** — 모든 tier read가 채널별이고, 프론트가 계정마다 하나씩 N번 읽어 흉내내고 있었다 |

그래서 만든 것은 **org-wide 리뷰 attention 질의 셋과 그것들을 모으는 read 하나**다. 나머지 세 영역은
각자의 소유자에게 그 소유자의 말로 물어 온다.

## 1. 왜 읽기가 하나인가

Home은 **채널의 기록도 계정의 큐도 아닌 유일한 화면**이고, 기존 attention read는 전부 둘 중 하나다.
클라이언트에서 합치면 채널 셋을 가진 판매자가 **더할 수 없는 숫자 셋**을 보게 된다 — rank 식은 같지만
「몇 건이 내 손을 기다리나」는 질문 하나이고 한 번 계산된 답 하나를 받아야 한다.

`GET /api/operations/home` · 컨트롤러에 **write 0**. Home은 일을 넘겨주지 소유하지 않는다 — 모든 행동은
그 결정을 이미 소유한 화면(리뷰 결정 워크스페이스 · 반복 문제 · 문의)으로 가는 링크다. 결정으로 가는 두
번째 문은 언젠가 첫 문과 다른 말을 한다.

**모델 호출 0.** 매일 아침 열리는 화면이 벤더 왕복을 사서는 안 된다.

## 2. urgency를 발명하지 않는 세 가지 장치

### 2-1. 어떤 칸도 두 숫자의 합이 아니다

기존 대시보드는 `urgentCount = unansweredInquiries + negativeReviews`를 들고 있다 — 실측 **24 + 19 = 43**.
서로 다른 두 모집단을 더해 아무도 세지 않은 셋째를 만들고 「urgent」라고 부른다. 43으로 행동하는 판매자는
**어떤 행 집합도 설명하지 않는 숫자**로 행동하는 것이다. 이 view에는 그런 칸이 없고
`OperationsHomeContractTest`가 이름으로 막는다(`urgent`·`urgency`·`score`·`priority`·`weight`·`combined`,
그리고 범위를 알 수 없는 맨 `total`·`count`·`pending`).

`needsAttentionTotal`·`watchTotal`은 **막지 않는다** — 각각 정확히 한 모집단을 세고 자기 이름에 어느
것인지 적혀 있다. 그것이 보호하려는 성질이지 위반이 아니다.

### 2-2. 「분류된 수」와 「지금 결정 필요한 수」가 다른 칸이다

tier는 리뷰의 read-time 함수라 **결정을 기록해도 tier는 바뀌지 않는다.** tier만 세면 이미 끝낸 일을 계속
요구하고, 미결정만 세면 tier 자체의 크기를 잃는다. 둘 다 있고 화면이 어느 쪽인지 말한다 —
실측 **확인 필요 15건 중 13건이 미결정**.

`WATCH`는 **관찰**이고 일이 아니다(실측 122건). 「같은 신호가 반복되면 무언가 바꿀 가치가 있다」는 반복
문제 lane의 질문이지 오늘의 결정 요청이 아니므로, 자기 칸으로 보고되고 **아무것에도 더해지지 않는다**.

### 2-3. 관찰 중 문제는 일처럼 그리지 않는다

`decidable`(확인 필요 + 조치 중)과 `observing`이 나뉜다. 실측 **관찰 중 16건 · 누군가의 차례 1건**.
「반복 문제 17건」이 할 일 목록 옆에 서면 관측 열여섯 개가 열여섯 개의 일로 보인다.

## 3. 네 영역

| # | 영역 | 진실의 소유자 | 나가는 길 |
|---|---|---|---|
| 1 | 지금 확인할 리뷰 | `TRIAGE_TIER_RANK`/`FINAL_TIER_RANK` + `NOT_DISMISSED_PREDICATE` (신규 org-wide 질의) | `/reviews/reply/{id}` — 결정 워크스페이스 |
| 2 | 반복 문제 | `ReviewIssueQueryService.list` + `RepeatedIssueWorkspaceService.context` | `/memory/{issueId}` |
| 3 | 최근 수집 상태 | `ChannelCoverageService` — `ChannelCoverageRow` **통째 재사용** | `/connect` |
| 4 | 준비된 작업 | 서 있는 승인 · 실제로 존재하는 초안 | 각 객체의 화면 |

**반복 문제 행은 workspace가 보이는 맥락을 그대로 들고 온다** — severity · trend · 근거 수 · **상품별
분모** · 별점 분포. 분모는 여기서도 **쌍이고 비율이 아니다**(실측 「리뷰 1,761건 중 16건」).
행마다 자기 context read를 사므로 **가장 세게 상한을 건다**(3건).

**「준비된 작업」은 어떤 기록이 존재한다고 말하는 것만 담는다.** phase는 초안이 아니다 — `PROPOSED`는
proposal이 기록될 때 쓰이고 `InquiryProposal`은 답변 본문을 저장하지 않는다(실측 PROPOSED 10 대 초안 2).
근거 없이 일을 만들어내지 않는다는 것은 **이 영역이 비었을 때 자라지 않는다**는 뜻이다.

**`detail`과 `label`을 나눈 이유**: 처음엔 한 문자열이었고 라이브에서 **「승인된 리뷰 답변」 네 줄**이 나왔다 —
열어 보지 않고는 고를 수 없는 링크 넷. 이제 행을 가르는 사실(상품 이름 · 리뷰 날짜, 문의는 그 제목)이
앞에 서고 일의 종류가 뒤따른다. 같은 상품의 승인 셋도 날짜로 갈린다.

## 4. 수집 상태 — 채널의 가장 나쁜 상태가 말한다

`ChannelCoverageRow` 셋(채널×타입)을 채널당 한 줄로 접되 **평균 내지 않는다** — 「수집이 잘 되고 있나」를
묻는 판매자는 **안 되고 있는 타입**에 대해 들어야 하고, 세 상태를 평균하면 아무도 계산하지 않은 넷째가 나온다.
freshness 판정은 서버의 것이고 이 줄은 어느 행이 말할지만 고른다.

**provider 기술명은 한 글자도 나가지 않는다** — connector 클래스 · data-type 토큰 · 오류 코드 없이
채널의 한국어 이름과 날짜뿐이고, 테스트가 렌더된 문자열로 확인한다.

**연결 안 됨 · 가져온 기록 없음 · 수집 못 하는 중**은 서로 다른 세 문장이다. `ZERO`만이 「없습니다」라고
말할 수 있다는 기존 규칙 그대로.

## 5. 실패와 빈손

- **읽기 실패 ⇒ 아무것도 그리지 않는다.** 질의가 죽어서 「확인 필요 0건」을 그리는 것은 **오류를 근거로
  판매자에게 아침이 한가하다고 말하는 일**이다. 대화는 별개 읽기라 그대로 돈다.
- **일도 연결도 없는 계정 ⇒ 아무것도 그리지 않는다.** 빈 제목 넷은 판매자가 아직 쓰지 않은 제품을 설명한다.
- 각 영역의 빈손은 **한 줄로 말하고 자라지 않는다**.

## 7. 고치지 않고 보고

- **기존 대시보드의 `urgentCount`는 그대로 있다.** `/api/dashboard/summary`가 여전히 43을 낸다.
  Operations Home은 쓰지 않지만 그 엔드포인트를 고치는 것은 이 패키지 밖이다.
- **사이드바의 「연결 문제 3건」은 오늘 stale이다.** 열린 `REPEATED_FAILURE` 알림 셋은 2026-08-18~23의
  것이고, 세 채널 모두 지금 `CONNECTED` · `consecutive_failures = 0`이며 **그 알림 이후에** 성공적으로
  수집했다(09-05 · 09-08). 그래서 Home의 수집 영역은 **연결 상태와 마지막 성공 수집에서 읽고 알림 행에서
  읽지 않는다** — 회복된 실패를 현재 문제로 그리는 것이 바로 이 브리프가 금지한 urgency 발명이다.
  알림 자체의 수명은 이 패키지가 건드리지 않았다.
- **1366/1152에서 아래 두 영역은 스크롤이 필요하다.** 리뷰 행을 5→3으로 줄이고 아래 두 영역을 나란히
  놓아 1440×900에서는 전부 들어가지만, 720px 높이에 네 영역과 docked composer를 함께 넣는 것은 내용을
  깎지 않고는 되지 않는다. 일하는 두 영역이 위에 있는 쪽을 택했다.
- **`observing` 16은 근거가 있는 이슈만 센다**(`IssueOrdering.hasLiveEvidence`). 전체 이슈 20건 중 3건은
  근거가 0이라 canonical 목록에서 빠진다 — 기존 성질이고 Home이 다시 정하지 않는다.
- `todayInbox.ts`의 세 builder와 `GET /api/proactive/summary`는 여전히 소비자 0이다(이 패키지 밖).
